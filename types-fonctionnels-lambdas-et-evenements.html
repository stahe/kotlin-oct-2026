    7. Types fonctionnels, lambdas et événements

    Dans de nombreux programmes, on a besoin de passer à une fonction non pas une donnée, mais un comportement : le critère d'un tri, la condition d'un filtrage, le traitement à exécuter quand quelque chose se produit. Kotlin répond à ce besoin en faisant des fonctions des valeurs comme les autres : une fonction a un type, le type fonctionnel, noté par exemple [(Int, Int) -> Int] ; on peut la ranger dans une variable, la passer en paramètre, la rendre comme résultat d'une autre fonction, et l'exécuter quand on le souhaite. Une fonction qui reçoit ou rend une fonction est dite d'ordre supérieur.

    Java, rappelons-le, n'a pas de types fonctionnels : il passe par les interfaces fonctionnelles, des interfaces n'ayant qu'une seule méthode abstraite ([Runnable], [Comparator], [Function<T, R>]…), et c'est seulement depuis Java 8 (2014) qu'il permet de les implémenter par des expressions lambda et des références de méthodes. Kotlin a eu les lambdas dès sa première version, et il sait aussi travailler avec les interfaces fonctionnelles de Java, puisqu'il utilise directement les bibliothèques Java. Nous avons déjà beaucoup utilisé les lambdas sans les détailler, avec les opérations sur les collections au chapitre 5 : dans [personnes.filter { it.age >= 18 }], on passe une lambda à la fonction [filter]. Ce chapitre explique ce qui se cache derrière cette écriture. Il se termine par les événements, que Kotlin, comme Java, gère avec des écouteurs (« listeners ») : des fonctions, le plus souvent des lambdas, qui s'inscrivent auprès d'un émetteur pour être averties de ce qui s'y passe. Les interfaces graphiques (Swing, JavaFX, Compose) comme les cadriciels web reposent sur ce mécanisme : un clic sur un bouton, l'arrivée d'une requête HTTP sont signalés à des écouteurs inscrits. Ce cours ne traite pas des interfaces graphiques : tous les exemples sont des programmes console.

    Les programmes du chapitre sont rangés dans le projet Gradle [07-lambdas], un paquetage par programme : [src/main/kotlin/lambdas01/Lambdas01.kt], [src/main/kotlin/lambdas02/Lambdas02.kt]… On les exécute par [gradlew -q run -Pmain=lambdas01.Lambdas01Kt] ou par le triangle vert d'IntelliJ IDEA. Le projet n'a besoin d'aucune bibliothèque en plus de la bibliothèque standard de Kotlin : les types fonctionnels, les lambdas et les fonctions de portée en font partie, et les interfaces du paquetage [java.util.function] sont celles du JDK.

    7.1. Les types fonctionnels et les interfaces fonctionnelles prédéfinies

    7.1.1. La notion de type fonctionnel

    Un type fonctionnel décrit un modèle (on dit aussi une signature, ou une forme) de fonction : les types de ses paramètres, entre parenthèses, puis une flèche, puis le type de son résultat. Une variable d'un type fonctionnel peut référencer n'importe quelle fonction de cette forme, et l'exécuter. Quelques exemples :

    • [() -> Unit] : une fonction sans paramètre qui ne rend aucun résultat utile ([Unit] joue le rôle du [void] de Java) ;
    • [() -> String] : une fonction sans paramètre qui rend une chaîne ;
    • [(Int) -> Boolean] : une fonction qui reçoit un entier et rend un booléen, autrement dit un prédicat ;
    • [(Int, Int) -> Int] : une fonction qui reçoit deux entiers et rend un entier ;
    • [(String) -> (Int) -> Int] : une fonction qui reçoit une chaîne et rend… une fonction de type [(Int) -> Int] (la flèche se lit de droite à gauche) ;
    • [(() -> Unit)?] : une fonction éventuellement absente ; les parenthèses sont nécessaires, car [() -> Unit?] désignerait une fonction rendant un [Unit?]. Nous retrouvons ici la sûreté vis-à-vis de [null] du chapitre 3 : on appelle une telle fonction par [f?.invoke()] ;
    • [String.(Int) -> String] : une fonction avec receveur ; elle s'applique à une chaîne, que son code désigne par [this], comme une fonction d'extension (chapitre 4). On peut l'appeler comme une extension (["ab".f(3)]) ou comme une fonction ordinaire dont le receveur est le premier paramètre ([f("ab", 3)]).

    Les paramètres peuvent être nommés, pour documenter le type : [(n1: Int, n2: Int) -> Int] est le même type que [(Int, Int) -> Int].

    Il existe trois façons d'obtenir une valeur de type fonctionnel :

    • écrire une référence de fonction vers une fonction existante qui a la bonne forme : [val tache: () -> Unit = ::afficher] ;
    • écrire une expression lambda : [val tache: () -> Unit = { println("tâche") }] ;
    • écrire une fonction anonyme : [val tache = fun() { println("tâche") }], ou un objet d'une classe qui implémente le type fonctionnel (un type fonctionnel est une interface, nous allons le voir). Ces deux écritures sont plus rares.

    On exécute ensuite la fonction comme une fonction ordinaire : [tache()]. C'est une écriture abrégée de l'appel de la méthode [invoke] de l'objet fonction : [tache.invoke()]. C'est une première différence visible avec Java, où l'on doit appeler la méthode de l'interface par son nom ([run], [apply], [test]…) ; Kotlin fait ici comme C#, où un délégué s'appelle comme une méthode.

    7.1.2. Types fonctionnels de Kotlin et interfaces de java.util.function

    Avant Java 8, chaque bibliothèque Java définissait ses propres interfaces à une méthode ([Runnable], [Comparator], [ActionListener]…). Java 8 a ajouté le paquetage [java.util.function], qui fournit 43 interfaces fonctionnelles génériques. Kotlin n'en a pas besoin : un type fonctionnel s'écrit directement. Mais ces interfaces restent utilisables depuis Kotlin, et on les rencontre dès que l'on appelle une bibliothèque Java.     Il n'y a pas, en Kotlin, de limite pratique au nombre de paramètres d'un type fonctionnel : [(Int, Int, Int) -> Int] s'écrit aussi simplement que les autres, alors qu'en Java, faute d'interface prédéfinie à trois paramètres, il faut définir la sienne.

    Comment la machine virtuelle Java, qui ne connaît que des classes et des interfaces, représente-t-elle un type fonctionnel ? Par des interfaces génériques de la bibliothèque de Kotlin : [kotlin.jvm.functions.Function0<R>], [Function1<P1, R>], [Function2<P1, P2, R>]… jusqu'à [Function22], puis une interface [FunctionN] au-delà. Chacune a une unique méthode [invoke] : [(Int, Int) -> Int] est compilé en [Function2<Integer, Integer, Integer>], dont la méthode est [operator fun invoke(p1: Int, p2: Int): Int]. C'est le modificateur [operator] de [invoke] (cf. la surcharge des opérateurs au chapitre 4) qui permet l'écriture [f(2, 3)]. Un type fonctionnel est donc, pour la JVM, une interface fonctionnelle comme celles de Java. Comme les génériques Java ne s'appliquent qu'aux types objets, les [Int] passés à un [(Int, Int) -> Int] sont convertis en [Integer] et inversement (boxing et unboxing). Java évite ces conversions avec ses interfaces spécialisées ([IntBinaryOperator]…) ; Kotlin les évite autrement, avec les fonctions [inline] que nous verrons plus loin.

    package lambdas01

import java.util.function.IntBinaryOperator
import java.util.function.Predicate
import java.util.function.Supplier

// les types fonctionnels de Kotlin et les interfaces fonctionnelles de Java

fun main() {
    // 1 - () -> Unit : aucun paramètre, aucun résultat
    val tache: () -> Unit = ::afficher
    // exécution : on appelle la fonction comme une fonction ordinaire
    tache()
    // ce qui est une écriture abrégée de l'appel de sa méthode invoke
    tache.invoke()

    // 2 - (Int, Int) -> Int : deux paramètres, un résultat
    val operation: (Int, Int) -> Int = ::ajouter
    println("operation(2, 3)=${operation(2, 3)}")
    // () -> String : aucun paramètre, un résultat
    val saluer: () -> String = ::saluer
    println("saluer()=${saluer()}")

    // 3 - (String) -> Unit : un paramètre, pas de résultat
    val ecrire: (String) -> Unit = ::println
    ecrire("(String) -> Unit a exécuté println")

    // 4 - (Int) -> Boolean : un prédicat
    val estPair: (Int) -> Boolean = ::estPair
    println("estPair(8)=${estPair(8)}")
    val nombres = mutableListOf(3, 8, 1, 6, 5, 4)
    // removeAll de la bibliothèque Kotlin attend un (Int) -> Boolean
    val modifiee = nombres.removeAll(estPair)
    println("nombres pairs retirés : $modifiee, reste : $nombres")

    // 5 - un Comparator<T> (interface Java) construit à partir d'une fonction (conversion SAM)
    val noms = mutableListOf("Paul", "Mélanie", "Jo", "Sébastien")
    noms.sortWith(Comparator(::comparerLongueurs))
    println("triés par longueur : $noms")

    // 6 - les interfaces de java.util.function restent utilisables
    val fournisseur: Supplier<String> = Supplier(::saluer)
    val multiplier = IntBinaryOperator(::multiplier)
    val predicat = Predicate<Int> { it > 4 }
    println("fournisseur.get()=${fournisseur.get()}")
    println("multiplier.applyAsInt(2, 3)=${multiplier.applyAsInt(2, 3)}")
    // removeIf est une méthode Java (Collection) : elle attend un Predicate
    val valeurs = mutableListOf(10, 3, 8, 7, 2, 1)
    valeurs.removeIf(predicat)
    // une fonction Kotlin est convertie automatiquement en Predicate (conversion SAM)
    valeurs.removeIf(estPair)
    valeurs.removeIf { it == 1 }
    println("après removeIf : $valeurs")

    // 7 - un type fonctionnel nullable : la fonction peut être absente
    executer(null)
    executer(tache)

    // 8 - un type fonctionnel avec receveur : String.(Int) -> String
    val repeter: String.(Int) -> String = String::repeat
    println("\"ab\".repeter(3)=${"ab".repeter(3)}, repeter(\"cd\", 2)=${repeter("cd", 2)}")

    // 9 - une fonction est un objet, instance d'une classe qui implémente une interface
    println("classe : ${operation::class.java.name}")
    println("interfaces : ${operation::class.java.interfaces.contentToString()}")
    val somme: (Int, Int) -> Int = { n1, n2 -> n1 + n2 }
    println("classe de la lambda : ${somme::class.java.name}")
    println("interfaces : ${somme::class.java.interfaces.contentToString()}")
}

// une fonction qui reçoit une fonction éventuellement absente
fun executer(rappel: (() -> Unit)?) {
    // appel sûr : rien n'est exécuté si rappel vaut null
    rappel?.invoke()
    println("rappel ${if (rappel == null) "absent" else "présent"}")
}

// les fonctions référencées : des fonctions de haut niveau du fichier
fun afficher() {
    println("afficher() exécutée par tache()")
}

fun ajouter(n1: Int, n2: Int): Int = n1 + n2

fun multiplier(n1: Int, n2: Int): Int = n1 * n2

fun saluer(): String = "Bonjour"

fun estPair(n: Int): Boolean = n % 2 == 0

fun comparerLongueurs(s1: String, s2: String): Int = s1.length.compareTo(s2.length)

    • ligne 60 : un type fonctionnel avec receveur. La référence [String::repeat] désigne la méthode [repeat] de la classe [String], qui s'applique à une chaîne et reçoit un entier. La classe de la référence de fonction [operation] (ligne 16 des résultats) est une classe générée par le compilateur Kotlin, nommée d'après l'endroit où la référence apparaît ; la classe de la lambda [somme] (ligne 18 des résultats) est générée à l'exécution par la machine virtuelle, comme pour les lambdas Java : son nom contient [$$Lambda] suivi d'une adresse qui change d'une exécution à l'autre. Dans les deux cas, la classe implémente l'interface [kotlin.jvm.functions.Function2] (lignes 17 et 19 des résultats). Une fonction Kotlin n'est donc pas un nouveau genre d'objet : c'est l'instance d'une classe ordinaire qui implémente une interface fonctionnelle.

    7.2. Définir ses propres types fonctionnels

    Les types fonctionnels suffisent souvent, mais on peut vouloir donner un nom à un modèle de fonction. Kotlin offre pour cela deux outils, de nature très différente.

    Le premier est l'alias de type, déclaré par le mot clé [typealias] :

    • [typealias OperationBinaire = (n1: Int, n2: Int) -> Int]

    Un alias ne crée aucun type nouveau : [OperationBinaire] est un autre nom de [(Int, Int) -> Int], et les deux écritures sont interchangeables. L'alias rend le code plus lisible quand le type fonctionnel est long ou revient souvent.

    Le second est l'interface fonctionnelle, déclarée par [fun interface] :

    • [fun interface Operation { fun calculer(n1: Int, n2: Int): Int }]

    C'est l'équivalent exact de l'interface fonctionnelle de Java : une interface qui n'a qu'une seule méthode abstraite (on dit aussi une interface SAM, « Single Abstract Method »). Elle peut avoir par ailleurs des méthodes avec un corps et des propriétés non abstraites : elles ne comptent pas. Le mot clé [fun] devant [interface] joue le rôle de l'annotation [@FunctionalInterface] de Java, avec une différence importante : il n'est pas facultatif. C'est lui qui autorise la conversion SAM, c'est-à-dire la création d'un objet [Operation] à partir d'une lambda ou d'une référence de fonction : [Operation { n1, n2 -> n1 + n2 }]. Sans le mot clé [fun], une interface Kotlin, même réduite à une méthode, ne peut être implémentée que par une classe ou par un objet anonyme ([object : Operation { … }]).

    Par rapport au type [(Int, Int) -> Int], le type [Operation] est un vrai type nouveau, distinct de tous les autres : il a un nom qui dit à quoi il sert, sa méthode a un nom parlant ([calculer] plutôt que [invoke]), il peut porter des méthodes supplémentaires, et il peut être implémenté par une classe nommée. En contrepartie, on l'exécute par le nom de sa méthode ([op.calculer(2, 3)]), et non par [op(2, 3)].

    Une variable [op] de type [Operation], comme une variable de type [(Int, Int) -> Int], ne référence qu'une seule fonction à la fois. Contrairement au C#, qui offre des « délégués multicast », ni Java ni Kotlin n'offrent le moyen d'enregistrer plusieurs fonctions dans une même variable pour les exécuter toutes d'un seul appel : quand on en a besoin, on range les fonctions dans une liste et on les exécute une à une. C'est exactement ce que nous ferons avec les écouteurs d'événements.

fun main() {

    var op = Operation(Calculs::augmenter)
    // on exécute l'opération
    var n = op.calculer(4, 7)
    println("n=$n")

    // création d'un objet c1 de type Calculs
    val c1 = Calculs()
    // on range dans op la méthode ajouter de l'objet c1
    op = Operation(c1::ajouter)
    n = op.calculer(2, 3)
    println("n=$n")
    // puis la méthode soustraire de c1
    op = Operation(c1::soustraire)
    n = op.calculer(2, 3)
    println("n=$n")

    // une variable ne référence qu'une fonction : pour en exécuter plusieurs, on utilise une liste
    val operations = listOf(
        Operation(c1::ajouter),
        Operation(c1::soustraire),
        Operation { n1, n2 -> n1 * n2 },
    )
    for (operation in operations) {
        println("-> ${operation.calculer(10, 4)}")
    }

    // une méthode de l'interface construit une nouvelle opération
    val sommeAuCarre = Operation(c1::ajouter).puis { x -> x * x }
    println("sommeAuCarre.calculer(1, 2)=${sommeAuCarre.calculer(1, 2)}")

    // Operation et IntBinaryOperator ont la même forme mais sont deux types différents
    val autre = IntBinaryOperator(op::calculer)
    println("autre.applyAsInt(5, 1)=${autre.applyAsInt(5, 1)}")

    // une interface fonctionnelle générique
    val longueur = Transformation(String::length)
    val etoiles = Transformation("*"::repeat)
    println("longueur(\"Bonjour\")=${longueur.transformer("Bonjour")}")
    println("etoiles(5)=${etoiles.transformer(5)}")

    // un alias de type : un simple autre nom pour (Int, Int) -> Int
    val f: OperationBinaire = { n1, n2 -> n1 - n2 }
    // OperationBinaire et (Int, Int) -> Int sont le même type
    val g: (Int, Int) -> Int = f
    // mais Operation est un type différent : il faut une conversion
    val op2 = Operation(g)
    println("f(5, 1)=${f(5, 1)}, g(5, 1)=${g(5, 1)}, op2.calculer(5, 1)=${op2.calculer(5, 1)}")
}

// définition d'une interface fonctionnelle : une seule méthode abstraite
// acceptant deux entiers en paramètres et rendant un entier
fun interface Operation {
    fun calculer(n1: Int, n2: Int): Int

    // une méthode avec un corps ne compte pas : l'interface reste fonctionnelle
    fun puis(suite: (Int) -> Int): Operation = Operation { n1, n2 -> suite(calculer(n1, n2)) }
}

// une interface fonctionnelle générique : T -> R
fun interface Transformation<T, R> {
    fun transformer(valeur: T): R
}

// un alias de type : aucun type nouveau n'est créé
typealias OperationBinaire = (n1: Int, n2: Int) -> Int

// une classe dont les méthodes ont la forme de l'interface Operation
class Calculs {
    // deux méthodes d'instance
    fun ajouter(n1: Int, n2: Int): Int {
        println("ajouter($n1,$n2)")
        return n1 + n2

    fun soustraire(n1: Int, n2: Int): Int {
        println("soustraire($n1,$n2)")
        return n1 - n2
    }

    // une méthode de l'objet compagnon : l'équivalent d'une méthode statique
    companion object {
        fun augmenter(n1: Int, n2: Int): Int {
            println("augmenter($n1,$n2)")
            return n1 + 2 * n2
        }
    }

// des objets anonymes aux expressions lambda

fun main() {
    // 1 - un objet anonyme : la classe qui implémente le type fonctionnel est écrite sur place
    val ajouter = object : (Int, Int) -> Int {
        override fun invoke(n1: Int, n2: Int): Int {
            return n1 + n2
        }
    }
    println("objet anonyme : ajouter(2, 3)=${ajouter(2, 3)}")

    // 2 - la même chose avec une expression lambda : { paramètres -> corps }
    val soustraire = { n1: Int, n2: Int -> n1 - n2 }
    println("lambda aux paramètres typés : soustraire(2, 3)=${soustraire(2, 3)}")

    // 3 - les types des paramètres sont déduits du type attendu
    val multiplier: (Int, Int) -> Int = { n1, n2 -> n1 * n2 }
    println("lambda aux paramètres non typés : multiplier(2, 3)=${multiplier(2, 3)}")

    // 4 - un seul paramètre : on peut ne pas le nommer, il s'appelle alors it
    val carre: (Int) -> Int = { it * it }
    val estVide: (String) -> Boolean = { s -> s.isEmpty() }
    println("carre(7)=${carre(7)}, estVide(\"\")=${estVide("")}")

    // 5 - aucun paramètre : pas de flèche
    val saluer = { "Bonjour" }
    val bip = { println("bip !") }
    println(saluer())
    bip()

    // 6 - un corps de plusieurs instructions : la valeur de la dernière expression est le résultat
    val repeter: (String, Int) -> String = { texte, fois ->
        val tampon = StringBuilder()
        for (i in 1..fois) {
            tampon.append(texte)
        }
        tampon.toString()
    }
    println(repeter("ab", 3))

    // 7 - paramètres inutilisés : _
    val ecouteur: (Any?, String) -> Unit = { _, _ -> println("événement reçu") }
    ecouteur(null, "clic")

    // 8 - une lambda passée en paramètre : hors des parenthèses si c'est le dernier paramètre
    val nombres = mutableListOf(3, 8, 1, 6, 5, 4)
    val pairs = nombres.filter { it % 2 == 0 }
    println("pairs : $pairs")
    nombres.sortWith { n1, n2 -> n2.compareTo(n1) }
    println("ordre décroissant : $nombres")
    // la lambda hors des parenthèses, après d'autres paramètres
    val total = nombres.fold(0) { acc, n -> acc + n }
    println("total : $total")

    // 9 - return dans une lambda : return@étiquette quitte la lambda seulement
    nombres.forEach {
        if (it % 2 == 0) return@forEach
        print("$it ")
    }
    println("<- impairs")
    // une étiquette choisie par le développeur
    nombres.forEach impair@{ n ->
        if (n % 2 != 0) return@impair
        print("$n ")
    }
    println("<- pairs")
    // une fonction anonyme : return y quitte la fonction anonyme
    val estGrand = fun(n: Int): Boolean {
        if (n > 5) return true
        return false
    }
    println("grands : ${nombres.filter(estGrand)}")

    // 10 - déstructuration des paramètres d'une lambda
    val ages = mapOf("Paul" to 40, "Mélanie" to 35)
    ages.forEach { (nom, age) -> println("$nom a $age ans") }
}

    Commentaires :

    • lignes 7-12 : un objet anonyme. Le mot clé [object] est suivi de deux-points, du type à implémenter, ici le type fonctionnel [(Int, Int) -> Int] (c'est une interface, nous l'avons vu), et du corps d'une classe qui implémente ce type en redéfinissant sa méthode [invoke]. Le compilateur génère une classe sans nom et en crée une instance. Six lignes pour exprimer [n1 + n2]. On l'exécute pourtant comme une fonction : [ajouter(2, 3)] ;
    • ligne 15 : la même chose avec une expression lambda. Une lambda s'écrit entre accolades : la liste des paramètres, l'opérateur [->] (une flèche, qui se lit « donne »), puis le corps. Le nom du type et celui de la méthode ont disparu. Comme les paramètres sont typés, le compilateur peut calculer le type de la lambda tout seul : [(Int, Int) -> Int]. C'est une différence avec Java, où une lambda n'a jamais de type par elle-même ;
    • ligne 19 : les types des paramètres ont disparu. Le compilateur les déduit du type attendu, déclaré pour la variable : [n1] et [n2] sont de type [Int]. C'est la forme la plus courante. Il n'y a pas, en Kotlin, de distinction entre « corps d'expression » et « corps de bloc » comme en Java : le corps d'une lambda est une suite d'instructions, et la valeur de la dernière expression est le résultat de la lambda ;
    • ligne 23 : avec un seul paramètre, on peut ne pas le déclarer du tout, ni la flèche : il s'appelle alors implicitement [it] (« lui », « cela »). [{ it * it }] se lit « son carré ». Ligne 24, le paramètre unique est nommé [s] : on le fait quand [it] rendrait le code moins lisible, notamment quand des lambdas sont imbriquées (chacune aurait son [it]) ;
    • lignes 28-29 : sans paramètre, il n'y a pas de flèche. Le type de [saluer] est inféré : [() -> String] ; celui de [bip] est [() -> Unit], puisque [println] rend [Unit] ;
    • lignes 34-39 : une lambda peut contenir n'importe quelles instructions : déclarations, boucles, tests… La valeur de la dernière expression, [tampon.toString()], est le résultat. On ne peut pas écrire [return tampon.toString()] : dans une lambda, un [return] sans étiquette ne quitte pas la lambda (voir plus bas) ;
    • ligne 44 : le caractère de soulignement [_] désigne un paramètre inutilisé. On l'utilise quand la forme du type impose des paramètres dont la lambda n'a pas besoin, ce qui est fréquent pour les écouteurs d'événements. On peut en écrire plusieurs dans la même lambda (Java a adopté cette écriture dans sa version 22) ;
    • lignes 48-49 : l'usage le plus fréquent des lambdas consiste à les passer directement en paramètre d'une fonction d'ordre supérieur. Quand la lambda est le dernier paramètre, on l'écrit hors des parenthèses ; s'il n'y a pas d'autre paramètre, les parenthèses disparaissent : [nombres.filter { it % 2 == 0 }] plutôt que [nombres.filter({ it % 2 == 0 })]. C'est cette règle qui donne au code Kotlin son allure particulière, et qui permet d'écrire des fonctions qui ressemblent à des instructions du langage ([repeat], [use], [thread], [synchronized]…). Comparez avec [Lambdas01.kt] : il n'est plus nécessaire d'écrire une fonction [estPair] ;
    • ligne 51 : une lambda qui inverse la comparaison usuelle : la liste est triée par ordre décroissant. [sortWith] attend un [Comparator] (une interface Java) : la conversion SAM est faite automatiquement ;
    • ligne 54 : la lambda reste hors des parenthèses quand la fonction a d'autres paramètres : [fold(0) { acc, n -> acc + n }]. La fonction [fold] (chapitre 5) part de la valeur initiale 0 et lui ajoute un à un les éléments ;
    • lignes 58-62 : dans une lambda, l'instruction [return@forEach] quitte la lambda (et passe donc à l'élément suivant), comme un [continue] dans une boucle. L'étiquette [@forEach] est implicite : c'est le nom de la fonction à laquelle la lambda est passée. Un [return] sans étiquette quitterait la fonction [main] tout entière : on l'appelle un retour non local, et il n'est permis que dans une lambda passée à une fonction [inline] comme [forEach] (nous verrons pourquoi) ;
    • lignes 64-68 : on peut aussi choisir l'étiquette, en la plaçant devant l'accolade ouvrante : [impair@{ … }], puis [return@impair] ;
    • lignes 70-74 : une fonction anonyme. Elle s'écrit comme une fonction ordinaire, sans nom. Son type est inféré : [(Int) -> Boolean]. Dans une fonction anonyme, [return] quitte la fonction anonyme elle-même. On l'utilise quand le corps comporte plusieurs points de sortie, ou quand on veut écrire explicitement le type du résultat ;
    • ligne 78 : les paramètres d'une lambda peuvent être déstructurés (chapitre 3). La lambda passée à [forEach] reçoit une entrée de la table associative ([Map.Entry<String, Int>]) ; l'écriture [(nom, age)], entre parenthèses, la décompose en sa clé et sa valeur. Attention : [{ nom, age -> … }] déclarerait deux paramètres, [{ (nom, age) -> … }] un seul paramètre décomposé.

    Une lambda n'est pas tout à fait un objet anonyme abrégé. Dans un objet anonyme, [this] désigne l'objet anonyme lui-même ; dans une lambda, [this] désigne l'objet de la méthode qui entoure la lambda (ou le receveur, pour une lambda avec receveur). De plus, un objet anonyme peut implémenter une interface à plusieurs méthodes, plusieurs interfaces à la fois, ou hériter d'une classe, ce qui est impossible avec une lambda. Dans le cours, nous utiliserons les lambdas chaque fois que c'est possible.

// compléments sur les lambdas et les références

fun main() {
    // 1 - le type d'une lambda est inféré de ses paramètres et de son corps...
    val doubler = { x: Int -> x * 2 }
    println("doubler(21)=${doubler(21)}")
    // ... ou fixé par le type attendu : le même texte de lambda peut donner trois types différents
    val fonction: () -> String = { "Bonjour" }
    val fournisseur = Supplier { "Bonjour" }
    val appelable = Callable { "Bonjour" }
    println("${fonction()} / ${fournisseur.get()} / ${appelable.call()}")

    // a) fonction de haut niveau : ::fonction
    val tripler: (Int) -> Int = ::tripler

    val nom = "Pierre"
    val enMajuscules: () -> String = nom::uppercase
    val longueurNom: () -> Int = nom::length
    println("enMajuscules()=${enMajuscules()}, longueurNom()=${longueurNom()}")
    // c) méthode d'un objet quelconque de la classe (référence non liée) : Classe::methode
    //    l'objet sur lequel la méthode est appelée devient le premier paramètre

import java.util.function.Function

// composer des fonctions : des fonctions qui rendent des fonctions

fun main() {
    // 1 - composition : nos extensions puis (d'abord this, ensuite l'autre) et apres (d'abord l'autre)
    val plusUn: (Int) -> Int = { it + 1 }
    val foisDeux: (Int) -> Int = { it * 2 }
    println("(plusUn puis foisDeux)(5)=${(plusUn puis foisDeux)(5)}")
    println("(plusUn apres foisDeux)(5)=${(plusUn apres foisDeux)(5)}")
    // les méthodes de l'interface Java Function restent disponibles
    val f = Function<Int, Int> { it + 1 }.andThen { it * 2 }
    println("Function.andThen : f.apply(5)=${f.apply(5)}")
    // une fonction qui fabrique des fonctions
    val plusDix = ajouteur(10)
    println("ajouteur(10)(5)=${plusDix(5)}, ajouteur(3)(5)=${ajouteur(3)(5)}")
    // une chaîne de traitements construite à partir d'une liste de fonctions
    val etapes: List<(String) -> String> = listOf(String::trim, String::lowercase, { it.replace(' ', '-') })
    val normaliser = etapes.fold({ s: String -> s }) { fonction, etape -> fonction puis etape }
    println("normaliser(\"  Mon Beau Titre \")=${normaliser("  Mon Beau Titre ")}")

    // 2 - prédicats : nos extensions et, ou, non
    val court: (String) -> Boolean = { it.length <= 4 }
    val commenceParP: (String) -> Boolean = { it.startsWith("P") }
    val prenoms = listOf("Paul", "Mélanie", "Jo", "Sébastien", "Pierre")
    println("court et P : ${filtrer(prenoms, court et commenceParP)}")
    println("court ou P : ${filtrer(prenoms, court ou commenceParP)}")
    println("non court : ${filtrer(prenoms, !court)}")
    // un prédicat sur CharSequence convient pour filtrer des String
    val nonVide: (CharSequence) -> Boolean = { it.isNotEmpty() }
    println("non vides : ${filtrer(listOf("a", "", "b"), nonVide)}")

    // 3 - plusieurs traitements sur la même valeur
    val journal = mutableListOf<String>()
    val afficher: (String) -> Unit = { println("affichage : $it") }
    val memoriser: (String) -> Unit = { journal.add(it) }
    val lesDeux = afficher aussi memoriser
    lesDeux("premier")
    lesDeux("second")
    println("journal : $journal")

    // 4 - comparateurs : compareBy, thenBy, thenByDescending, reversed
    val personnes = mutableListOf(Personne("Paul", 32), Personne("Mélanie", 25),
        Personne("Jo", 32), Personne("Sébastien", 25))
    personnes.sortWith(compareBy(Personne::age).thenBy(Personne::nom))
    println("par âge puis nom : $personnes")
    personnes.sortWith(compareBy(Personne::age).reversed().thenByDescending(Personne::nom))
    println("par âge décroissant puis nom décroissant : $personnes")
    // plusieurs critères d'un coup
    personnes.sortWith(compareBy({ it.nom.length }, { it.nom }))
    println("par longueur du nom puis nom : $personnes")
    // un comparateur sert aussi à choisir le plus petit de deux éléments
    val parAge = compareBy(Personne::age)
    println("plus jeune de Paul et Mélanie : ${minOf(personnes[1], personnes[2], parAge)}")
}

fun <T> filtrer(elements: List<T>, predicat: (T) -> Boolean): List<T> {
    val resultat = mutableListOf<T>()
    for (element in elements) {
        if (predicat(element)) {
            resultat.add(element)
        }
    }
    return resultat

    println("A : ${compteurA()} ${compteurA()} ${compteurA()}")

    val actions = mutableListOf<() -> Unit>()
    for (i in 0..2) {
        actions.add { print("$i ") }
    }
    print("for : ")
    actions.forEach { it() }
    println()

        actions.add { print("$k ") }
        k++
    }
    print("while, capture de la var k : ")
    actions.forEach { action -> action() }
    println()
}

Le compilateur Kotlin fait le travail que le développeur Java doit faire à la main : une variable locale [var] capturée et modifiée n'est plus rangée dans la pile, mais dans un petit objet de la classe [kotlin.jvm.internal.Ref.IntRef] (il en existe une par type de base, et [Ref.ObjectRef] pour les références), qui a un unique champ modifiable, [element]. La fonction [main] et la lambda partagent cet objet : chaque lecture ou écriture de [total], dans l'une ou dans l'autre, devient une lecture ou une écriture de [total.element]. On le vérifie par la réflexion : l'unique champ de l'objet lambda est de type [Ref$IntRef] (ligne 5 des résultats). C'est exactement ce que fait le compilateur C# avec ses variables capturées ;
    • lignes 31-34 : une lambda peut aussi lire et modifier une variable de haut niveau (ligne 6) ou une propriété de l'objet courant. Il n'y a là rien à capturer : la variable de haut niveau est un champ statique de la classe [Lambdas06Kt] ; pour une propriété, la lambda capture la référence [this] ;
    • lignes 64-67 : la fonction [creerCompteur] rend une lambda qui capture et modifie sa variable locale [valeur]. Normalement, une variable locale disparaît quand la fonction se termine. Ici, la variable est rangée dans un objet [Ref.IntRef] référencé par la lambda : elle survit à [creerCompteur] tant que la lambda existe. L'ensemble formé par la lambda et les variables qu'elle capture s'appelle une fermeture (« closure ») ;
    • lignes 37-40 : chaque appel de [creerCompteur] crée une nouvelle variable [valeur], donc un nouveau compteur, indépendant des autres. Les résultats (lignes 7-8) le confirment ;
    • lignes 44-48 : dans une boucle [for] de Kotlin, la variable [i] est une [val], nouvelle à chaque tour : chaque lambda capture la sienne, et les trois lambdas affichent 0, 1 et 2. On remarque qu'une liste de fonctions s'exécute par [actions.forEach { it() }] : [it] est une fonction, que l'on appelle ;
    • lignes 53-59 : voici le revers de la liberté de Kotlin. La boucle [while] utilise une seule variable [k], modifiée à chaque tour. Les trois lambdas capturent la même variable, et l'affichent quand elles s'exécutent, c'est-à-dire après la boucle, quand elle vaut 3 : elles affichent toutes 3 (ligne 10 des résultats). Java élimine ce piège à la compilation ; en Kotlin, c'est au développeur d'y penser. La solution est la même qu'en Java : déclarer dans le corps de la boucle une [val] nouvelle à chaque tour ([val copie = k]) et capturer celle-ci, ou, mieux, utiliser une boucle [for].

    La règle de Java a une justification solide : une lambda peut être exécutée plus tard, ou dans un autre thread (chapitre 8). Si elle peut modifier les variables locales d'une fonction, ou les lire pendant qu'un autre thread les modifie, on peut obtenir des comportements difficiles à prévoir. Kotlin fait un autre choix, plus pratique : la capture des [var] est permise, mais les objets [Ref] ne sont pas protégés contre les accès simultanés. Retenons donc que la capture d'une [var] est sans danger dans un programme à un seul thread et dans les lambdas exécutées immédiatement ([forEach], [filter]…), mais que, dès qu'une lambda peut s'exécuter dans un autre thread, l'état modifiable partagé doit être rendu explicite, avec un objet dont on choisit le comportement vis-à-vis des threads ([AtomicInteger], collection concurrente…). Nous y reviendrons aux chapitres 8 et 9. Les fonctions [inline], présentées plus loin, évitent d'ailleurs la création des objets [Ref] quand la lambda est recopiée dans le code appelant.

    7.4. Fonctions inline et fonctions de portée

    7.4.1. Les fonctions inline

    Une lambda est un objet. Passer une lambda à une fonction d'ordre supérieur a donc un coût : la création de l'objet (sauf pour une lambda qui ne capture rien, que la machine virtuelle peut réutiliser), l'appel de sa méthode [invoke], les conversions [Int] ↔ [Integer] imposées par les interfaces génériques [Function1], [Function2]…, et les objets [Ref] des variables capturées. Pour une fonction comme [filter], appelée sur chaque élément de collections parfois très grandes, ce coût compte. Kotlin le supprime avec le modificateur [inline] : quand une fonction est déclarée [inline fun], le compilateur ne génère pas d'appel à cette fonction ; il recopie son code à chaque endroit où elle est appelée, et il y recopie aussi le code des lambdas qu'on lui passe. Il n'y a plus alors ni objet lambda, ni appel de [invoke], ni conversion. Les fonctions de la bibliothèque standard qui reçoivent des lambdas ([forEach], [filter], [map], [fold], [let], [apply], [repeat], [use], [synchronized]…) sont presque toutes [inline]. Java n'a pas d'équivalent : il compte sur le compilateur à la volée de la machine virtuelle pour obtenir un résultat comparable à l'exécution.

    L'insertion du code a une seconde conséquence, plus visible : puisque le code de la lambda est recopié dans la fonction appelante, une instruction [return] sans étiquette peut y quitter la fonction appelante. C'est le retour non local rencontré avec [forEach] dans [Lambdas03.kt]. Deux modificateurs complètent [inline] :

    • [noinline], sur un paramètre fonctionnel d'une fonction [inline], demande que la lambda correspondante ne soit pas recopiée, mais passée comme un objet ordinaire. C'est nécessaire quand la fonction veut conserver la lambda (la ranger dans une liste, la rendre comme résultat…) : du code recopié ne peut pas être rangé dans une liste ;
    • [crossinline] demande que la lambda soit recopiée, mais interdit le retour non local. C'est nécessaire quand la fonction [inline] n'exécute pas la lambda elle-même, mais dans un autre contexte, par exemple dans un objet [Runnable] qu'elle crée : quand le [Runnable] s'exécutera, la fonction appelante sera peut-être terminée depuis longtemps, et un [return] ne pourrait plus la quitter.

fun executer(bloc: () -> Unit) {
    bloc()
}

// une fonction inline : son code, et celui de la lambda, sont recopiés à l'endroit de l'appel
inline fun executerInline(bloc: () -> Unit) {
    bloc()
}

// notre propre forEach, inline comme celui de la bibliothèque
inline fun <T> pourChaque(elements: List<T>, action: (T) -> Unit) {
    for (element in elements) action(element)
}

fun premierPair(nombres: List<Int>): Int? {
    pourChaque(nombres) {
        // retour non local : on quitte premierPair, et pas seulement la lambda
        if (it % 2 == 0) return it
    }
    return null
}

// immediat est recopiée ; memorise reste un objet fonction, que l'on peut ranger dans la liste
inline fun executerPuisMemoriser(
    rappels: MutableList<() -> Unit>,
    immediat: () -> Unit,
    noinline memorise: () -> Unit,
) {
    immediat()
    rappels.add(memorise)
}

// action est exécutée dans un objet Runnable, et non dans enTache : un retour non local y est impossible
inline fun enTache(crossinline action: () -> Unit): Runnable = Runnable { action() }

    7.4.2. Les fonctions de portée

    La bibliothèque standard de Kotlin offre cinq petites fonctions [inline], très utilisées, appelées fonctions de portée (« scope functions ») : [let], [run], [with], [apply] et [also]. Elles ne font presque rien : chacune exécute une lambda sur un objet. Elles diffèrent sur deux points :

    • la façon dont la lambda désigne l'objet : soit comme son paramètre [it] (la lambda est de type [(T) -> R]), soit comme son receveur [this], que l'on peut alors omettre (la lambda est une lambda avec receveur, de type [T.() -> R], cf. [Lambdas01.kt]) ;
    • ce que rend la fonction : soit le résultat de la lambda, soit l'objet lui-même.

// les fonctions de portée : let, run, with, apply, also (et takeIf)

fun main() {
    // 1 - apply : configure l'objet (this) et rend l'objet
    val paul = Personne("Paul").apply {
        age = 32
        ville = "Angers"
    }
    println("apply : $paul")

    // 2 - also : un traitement supplémentaire sur l'objet (it), qui est rendu
    val personnes = mutableListOf<Personne>()
    val melanie = Personne("Mélanie", 25).also { personnes.add(it) }
    println("also : $melanie, personnes=$personnes")

    // 3 - let : transforme l'objet (it) en un résultat ; très utilisé avec ?.
    val longueur = paul.nom.let { it.length * 2 }
    println("let : longueur=$longueur")
    for (ville in listOf("Tours", null)) {
        val message = ville?.let { "habite à ${it.uppercase()}" } ?: "ville inconnue"
        println("let et ?. : $message")
    }

    // 4 - run : un calcul sur l'objet (this), qui rend un résultat
    val description = paul.run { "$nom, $age ans, habite à $ville" }
    println("run : $description")

    // 5 - with : comme run, mais l'objet est passé en paramètre
    val resume = with(StringBuilder()) {
        append("Personnes : ")
        append(personnes.joinToString { it.nom })
        toString()
    }
    println("with : $resume")

    for (age in listOf(15, 40)) {
        val majeur = Personne("Jo", age).takeIf { it.age >= 18 }
        println("takeIf : ${majeur ?: "mineur"}")
    }
}

    7.5. Types fonctionnels, interfaces fonctionnelles ou interfaces ?

    Ces deux exemples montrent qu'en Kotlin comme en Java, une fonction qui attend un comportement accepte à la fois des objets de classes écrites pour l'occasion, des références et des lambdas. Il reste deux questions. La première est propre à Kotlin : pour un paramètre fonctionnel, faut-il un type fonctionnel ou une [fun interface] ?

    • le type fonctionnel est le choix par défaut. Il ne demande aucune déclaration, il s'appelle comme une fonction, il accepte directement les lambdas et les références, et il profite des fonctions [inline]. Un [typealias] lui donne un nom quand il est long ;
    • la fun interface se justifie quand on veut un type vraiment distinct (qu'on ne puisse pas confondre avec une autre fonction de même forme), une méthode au nom parlant, des méthodes supplémentaires avec un corps, ou une API destinée aussi à des appelants Java : pour Java, une [fun interface] est une interface fonctionnelle ordinaire, utilisable avec ses lambdas, alors qu'un type fonctionnel Kotlin lui apparaît comme une [Function2<Integer, Integer, Integer>] dont la méthode [invoke] doit rendre un objet ([Unit] pour une fonction « sans résultat »).

    La seconde question est la même qu'en Java : faut-il que l'interface ait une seule méthode, ou plusieurs ?

    • une fonction, type fonctionnel ou interface à une seule méthode, se montre plus souple d'utilisation : toute fonction existante ayant la bonne forme fait l'affaire, et une lambda permet même d'écrire la fonction à l'endroit de l'appel. Il n'y a pas de classe à écrire. Cette souplesse explique que les bibliothèques modernes (les collections, les coroutines du chapitre 9, Spring) utilisent massivement les paramètres fonctionnels ;
    • une interface à plusieurs membres reprend l'avantage dès que le comportement à transmettre comporte plusieurs opérations liées entre elles ([calculer] et [nom] ci-dessus), ou qu'il a besoin d'un état et d'une identité propres.

    C'est le cas de l'interface [IImpotDao] de la couche [dao] du chapitre 6 : bien qu'elle n'ait qu'un membre, la propriété [val tranchesImpot: List<TrancheImpot>], ses implémentations ont un état (les tranches lues, le nom du fichier), sont créées par le conteneur d'injection de dépendances et représentent un rôle clairement nommé de l'application. Un [() -> List<TrancheImpot>] aurait techniquement suffi, mais il aurait été beaucoup moins parlant. On réserve donc les types fonctionnels aux comportements courts et ponctuels (un critère, une transformation, une action), et les interfaces « métier » aux rôles de l'application, quel que soit leur nombre de membres.

    7.6. Gestion d'événements

    7.6.1. Le modèle des écouteurs

    Les fonctions passées en paramètre servent à mettre en place des événements. Pas plus que Java, Kotlin n'a de mot clé dédié aux événements (le C# a son mot clé [event]) : il utilise les conventions établies par Java dès sa version 1.1 pour les composants graphiques et les JavaBeans, appelées le modèle des écouteurs (« listener model »). Une classe [C1] qui veut signaler un événement [Xxx] procède ainsi :

    • une classe [XxxEvent] encapsule les informations sur l'événement, dont l'objet à l'origine de l'événement, qu'on appelle la source. En Java, la convention veut qu'elle dérive de [java.util.EventObject], qui mémorise la source ; en Kotlin, une classe ordinaire avec des propriétés en lecture seule suffit, et c'est ce que nous ferons ;
    • un type d'écouteur définit la forme de la fonction qui sera appelée quand l'événement se produit. En Java, c'est une interface [XxxListener] ; en Kotlin, c'est le plus souvent un simple type fonctionnel, [(XxxEvent) -> Unit], nommé par un [typealias] : un écouteur sera une lambda ou une référence de fonction ;
    • la classe [C1] gère une liste de fonctions et offre deux méthodes publiques pour s'y inscrire et s'en désinscrire : [addXxxListener(listener)] et [removeXxxListener(listener)] ;
    • lorsqu'une instance [c1] de [C1] veut signaler l'événement, elle crée un objet [XxxEvent] et appelle chacun des écouteurs inscrits en lui passant cet objet. Par convention, cette notification est confiée à une méthode protégée [fireXxx(e: XxxEvent)] (« fire » : déclencher), qu'une classe dérivée peut redéfinir pour modifier la façon dont l'événement est publié ;
    • si un objet [c2] veut être averti de l'événement [Xxx] de l'objet [c1], il s'inscrit par [c1.addXxxListener(...)]. Il pourra se désinscrire par [c1.removeXxxListener(...)] lorsqu'il ne voudra plus être averti. Comme [c1] gère une liste, différents objets peuvent s'inscrire pour être prévenus du même événement.

    Dans ce scénario, on a :

    • une classe qui signale (on dit aussi publie, ou émet) un événement ;
    • des objets qui sont avertis de cet événement. On dit qu'ils s'abonnent, ou s'inscrivent, à l'événement : ce sont les écouteurs (« listeners »), ou gestionnaires d'événement ;
    • un type d'écouteur qui définit la forme des fonctions qui seront averties de l'événement.

    C'est le patron de conception Observateur (« Observer ») : l'émetteur ne connaît pas ses abonnés, il se contente de les avertir. Ce modèle offre la même protection qu'un mot clé dédié : la liste des écouteurs est une propriété privée de l'émetteur. De l'extérieur, on ne peut que s'inscrire ou se désinscrire ; on ne peut ni vider la liste, ni remplacer les écouteurs des autres, ni déclencher l'événement à la place de l'émetteur.

    7.6.2. Un exemple : la température trop haute

    Considérons l'exemple suivant :

    • une classe [Emetteur] encapsule une température. Lorsque cette température dépasse un certain seuil, un événement doit être signalé. Nous appellerons cet événement [TemperatureTropHaute]. Les informations sur cet événement seront encapsulées dans un objet [TemperatureTropHauteEvent] et les écouteurs seront des fonctions de type [TemperatureTropHauteListener] ;
    • une classe [Souscripteur] s'inscrit comme écouteur de l'événement précédent. Lorsqu'elle est avertie de l'événement, elle affiche un message sur la console. Un souscripteur se désinscrit de lui-même après avoir reçu un nombre donné d'alertes ;
    • un programme console crée un émetteur et deux souscripteurs. Il saisit des températures au clavier et les enregistre dans l'émetteur. Si l'une d'elles est trop haute, l'émetteur signale l'événement [TemperatureTropHaute].

// une classe qui s'inscrit comme écouteur de l'événement
class Souscripteur(

    private val nom: String,
    // nombre maximal d'alertes acceptées
    private val nbAlertesMax: Int,

    private var nbAlertes = 0

        emetteur.addTemperatureTropHauteListener(::evtTemperatureTropHaute)

    // désinscription : une nouvelle référence à la même méthode du même objet lui est égale

    // gestionnaire de l'événement TemperatureTropHaute
    private fun evtTemperatureTropHaute(e: TemperatureTropHauteEvent) {

        val temperature = "%.1f".format(e.temperature)
        println("Souscripteur [$nom] : la source [${emetteur.nom}] " +
            "a signalé une température trop haute : [$temperature]")
        // au-delà de nbAlertesMax alertes, le souscripteur se désinscrit
        nbAlertes++
        if (nbAlertes == nbAlertesMax) {

            println("Souscripteur [$nom] : désabonné après $nbAlertes alerte(s)")

    }

    • lignes 19-20 : la désinscription passe à [removeTemperatureTropHauteListener] une nouvelle référence [::evtTemperatureTropHaute]. En Java, ce serait une erreur classique : deux évaluations de [this::evtTemperatureTropHaute] produisent deux objets que [equals] considère comme différents, et la désinscription ne retirerait rien, sans aucun message d'erreur ; il faut créer l'écouteur une seule fois et le conserver dans un champ. Nous avons vu avec [Lambdas04.kt] qu'en Kotlin, deux références à la même fonction du même objet sont égales : [remove] retrouve donc l'écouteur inscrit, et seulement lui, puisque les références des autres souscripteurs sont liées à d'autres objets. Ce ne serait pas le cas d'une lambda : [{ e -> evtTemperatureTropHaute(e) }], écrite deux fois, donnerait deux objets différents ;
    • ligne 24 : le gestionnaire de l'événement. Il a la forme imposée par le type [TemperatureTropHauteListener]. Il est privé : seul le souscripteur peut l'inscrire auprès d'un émetteur. Une autre façon de faire consiste à faire implémenter le type d'écouteur par la classe [Souscripteur] elle-même ([class Souscripteur : TemperatureTropHauteListener], avec une méthode [invoke]) et à s'inscrire avec [this]. Elle a l'inconvénient de rendre publique la méthode [invoke], que n'importe qui pourrait alors appeler ;
    • ligne 25 : la source de l'événement est directement de type [Emetteur] ;
    • lignes 26-28 : le gestionnaire affiche le nom du souscripteur, le nom de l'émetteur qui a signalé l'événement et la température qui l'a déclenché. Le format [%.1f] affiche le réel avec un chiffre après la virgule, selon les conventions françaises (la fonction [format] de Kotlin utilise les conventions locales de la machine). La chaîne est écrite en deux morceaux concaténés par [+] pour que la ligne tienne dans la page ;

    7.6.3. Les événements de changement de propriété

    Le cas le plus fréquent d'événement est celui où une propriété d'un objet change de valeur : un autre objet (une interface graphique, un cache, un journal) veut en être averti. Kotlin et la bibliothèque Java offrent pour ce cas deux outils complémentaires :

    • les propriétés déléguées de Kotlin. Une propriété déclarée [var p: T by delegue] confie la lecture et l'écriture de sa valeur à un autre objet, le délégué. La bibliothèque standard en fournit plusieurs, comme [by lazy { … }], qui calcule la valeur de la propriété au premier accès. L'objet [kotlin.properties.Delegates] fournit deux délégués qui reçoivent une lambda : [Delegates.observable(valeurInitiale) { propriete, ancienne, nouvelle -> … }] exécute la lambda après chaque écriture de la propriété ; [Delegates.vetoable(valeurInitiale) { propriete, ancienne, nouvelle -> … }] l'exécute avant, et n'accepte la nouvelle valeur que si la lambda rend [true]. Le paramètre [propriete] est une référence à la propriété ([KProperty]), dont on obtient le nom par [propriete.name] ;
    • la classe Java [java.beans.PropertyChangeSupport], qui gère la liste des écouteurs à notre place. Les écouteurs implémentent l'interface fonctionnelle [PropertyChangeListener], dont la méthode [void propertyChange(PropertyChangeEvent evt)] reçoit un événement contenant la source, le nom de la propriété, son ancienne et sa nouvelle valeur.

// les événements de changement de propriété : Delegates.observable, vetoable et PropertyChangeSupport

fun main() {
    val thermometre = Thermometre("salon")
    // un écouteur de toutes les propriétés
    val journal = PropertyChangeListener { e ->
        val source = e.source as Thermometre
        println("Journal : ${source.nom}.${e.propertyName} : ${e.oldValue} -> ${e.newValue}")
    }
    thermometre.addPropertyChangeListener(journal)
    // un écouteur de la seule propriété temperature
    thermometre.addPropertyChangeListener("temperature") { e ->
        if (e.newValue as Double > 19) {
            println("Alerte : température trop haute")
        }
    }

    thermometre.temperature = 18.0
    thermometre.temperature = 21.5
    // même valeur : aucun événement
    thermometre.temperature = 21.5
    thermometre.nom = "séjour"
    // désinscription du journal
    thermometre.removePropertyChangeListener(journal)
    thermometre.temperature = 22.0
    println("écouteurs restants : ${thermometre.nbEcouteurs}")

    // une propriété qui peut refuser une nouvelle valeur
    for (valeur in listOf(21.0, 45.0)) {
        thermometre.consigne = valeur
        println("consigne demandée : $valeur, consigne retenue : ${thermometre.consigne}")
    }
}

// une classe dont les propriétés signalent leurs changements
class Thermometre(nom: String) {
    // la gestion des écouteurs est déléguée à un objet PropertyChangeSupport
    private val changements = PropertyChangeSupport(this)

    // une propriété observable : après chaque écriture, on signale le changement
    private fun <T> observable(valeurInitiale: T): ReadWriteProperty<Any?, T> =
        Delegates.observable(valeurInitiale) { propriete, ancienne, nouvelle ->
            changements.firePropertyChange(propriete.name, ancienne, nouvelle)
        }

    var nom: String by observable(nom)
    var temperature: Double by observable(0.0)

    // une propriété qui refuse les valeurs hors de l'intervalle [5, 30]
    var consigne: Double by Delegates.vetoable(20.0) { _, _, nouvelle -> nouvelle in 5.0..30.0 }

    // inscription et désinscription des écouteurs
    fun addPropertyChangeListener(listener: PropertyChangeListener) {
        changements.addPropertyChangeListener(listener)
    }

    fun addPropertyChangeListener(propriete: String, listener: PropertyChangeListener) {
        changements.addPropertyChangeListener(propriete, listener)
    }

    fun removePropertyChangeListener(listener: PropertyChangeListener) {
        changements.removePropertyChangeListener(listener)
    }

    val nbEcouteurs: Int
        get() = changements.propertyChangeListeners.size
}

// les lambdas, les collections et les séquences

fun main() {
    val nombres = listOf(3, 8, 1, 6, 5, 4, 9, 2)

    // 1 - filter et map attendent des fonctions (T) -> Boolean et (T) -> R
    val estPair: (Int) -> Boolean = { it % 2 == 0 }
    val carre: (Int) -> Int = { it * it }
    println("collections : ${nombres.filter(estPair).map(carre)}")
    // l'API Stream de Java reste utilisable : les lambdas sont converties en Predicate et Function
    println("Stream : ${nombres.stream().filter { it % 2 == 0 }.map { it * it }.toList()}")

    // 2 - notre propre fonction de filtrage, appelée avec une lambda puis une référence
    println("filtrer(n > 4) : ${nombres.filtrer { it > 4 }}")
    println("filtrer(estImpair) : ${nombres.filtrer(::estImpair)}")

    // 3 - une collection est évaluée immédiatement : chaque étape produit une liste complète
    val grandsListe = nombres.filter {
        print("[test $it] ")
        it > 7
    }
    println()
    println("la liste est déjà calculée : $grandsListe")

    // 4 - une séquence est évaluée à la demande :
    //     le prédicat n'est appelé que par l'opération terminale
    val grands = nombres.asSequence().filter {
        print("[test $it] ")
        it > 7
    }
    println("la séquence est définie, rien n'a encore été exécuté")
    grands.forEach { print("-> $it ") }
    println()

    // 5 - nos propres opérations intermédiaires sur les séquences, paresseuses elles aussi
    val villes = listOf("Angers", "Paris", "Lyon", "Nantes", "Aix")
    val resultat = villes.asSequence()
        .garder { it.length <= 5 }
        .transformer(String::uppercase)
        .toList()
    println("nos opérations : $resultat")
    // une séquence infinie : seuls les éléments demandés sont calculés
    val puissancesDeDeux = generateSequence(1) { it * 2 }
    val premieres = puissancesDeDeux.transformer { "2^${it.countTrailingZeroBits()}=$it" }.take(5)
    println("puissances de 2 : ${premieres.toList()}")
}

// filtre une liste avec un prédicat : le travail que fait filter
inline fun <T> List<T>.filtrer(predicat: (T) -> Boolean): List<T> {
    val resultat = mutableListOf<T>()
    for (element in this) {
        if (predicat(element)) {
            resultat.add(element)
        }
    }
    return resultat
}

fun estImpair(n: Int) = n % 2 != 0

// une opération intermédiaire de séquence qui ne laisse passer que les éléments vérifiant le prédicat
fun <T> Sequence<T>.garder(predicat: (T) -> Boolean): Sequence<T> = sequence {
    for (element in this@garder) {
        if (predicat(element)) yield(element)
    }
}

// une opération intermédiaire qui transforme chaque élément : l'équivalent de map
fun <T, R> Sequence<T>.transformer(transformation: (T) -> R): Sequence<R> = sequence {
    for (element in this@transformer) {
        yield(transformation(element))
    }
}

Elle n'est utilisable que grâce à l'évaluation paresseuse : [take(5)] ne demande que les cinq premiers éléments, et seuls ceux-ci sont calculés. La lambda passée à [transformer] affiche chaque puissance sous la forme [2^n=valeur] ([countTrailingZeroBits] compte les zéros de droite de l'écriture binaire, c'est-à-dire l'exposant).

Pour les collections, elles sont [inline] et immédiates ; pour les séquences, elles conservent les lambdas et ne calculent les éléments qu'à la demande de l'opération terminale.

    7.8. Les arbres d'expression

    Certains langages, comme C#, permettent de convertir une lambda non pas en code exécutable, mais en une structure de données qui la décrit (un « arbre d'expression ») : un programme peut alors analyser la lambda [t => t.Limite > 20000] et la traduire, par exemple, en une clause SQL [WHERE limite > 20000] exécutée par le serveur de bases de données.

    Kotlin, pas plus que Java, n'a d'équivalent : une lambda Kotlin est toujours compilée en code exécutable ; on peut l'appeler, mais on ne peut pas examiner ce qu'elle fait. Plusieurs outils s'en approchent cependant :

    • les références de propriétés : [Personne::age] est un objet ([KProperty1<Personne, Int>]) qui connaît le nom de la propriété ([Personne::age.name]) et son type. Une bibliothèque peut s'en servir pour construire une requête sans écrire de chaîne : c'est ce que fait par exemple Spring Data MongoDB avec ses extensions Kotlin, qui permettent d'écrire un critère comme [Personne::age gt 18] ;
    • les DSL (« Domain Specific Languages ») internes : grâce aux lambdas avec receveur, aux fonctions [infix] et à la surcharge des opérateurs, une bibliothèque Kotlin peut offrir une syntaxe proche de SQL, que le programme exécute pour construire une structure de données décrivant la requête. C'est le principe de la bibliothèque Exposed, de JetBrains : [Tranches.selectAll().where { Tranches.limite greater 20000 }] ;
    • les greffons du compilateur (« compiler plugins ») : le compilateur Kotlin peut être étendu par des greffons qui transforment le code. C'est ainsi que fonctionnent kotlinx.serialization, les greffons [all-open] et [no-arg] utilisés avec Spring et Hibernate, ou le greffon [power-assert], qui analyse l'expression d'une assertion pour en afficher le détail en cas d'échec. Mais il s'agit d'outils de construction, et non d'une fonctionnalité offerte au programme.

    Hibernate, que nous étudierons au chapitre 11, propose pour sa part les mêmes solutions qu'en Java : un langage de requêtes proche de SQL mais exprimé en termes de classes et de propriétés, HQL (["from Tranche t where t.limite > 20000"]), et l'API Criteria de Jakarta Persistence, qui construit la requête par des appels de méthodes ([cb.gt(t.get("limite"), 20000)]). Dans les deux cas, la requête est une donnée (une chaîne ou un arbre d'objets) que Hibernate traduit en SQL, alors qu'une lambda passée à [filter] s'exécute dans le programme Kotlin.

    7.9. Conclusion

    Nous retiendrons de ce chapitre :

    • en Kotlin, les fonctions sont des valeurs : elles ont un type fonctionnel ([(Int, Int) -> Int], [() -> Unit], [(T) -> Boolean], [(() -> Unit)?], [T.() -> R]…), se rangent dans des variables, se passent en paramètre, se rendent comme résultat, et s'appellent comme des fonctions ordinaires. Pour la machine virtuelle, ce sont des objets qui implémentent les interfaces [Function0], [Function1]… ;
    • les interfaces de [java.util.function] ([Function], [Supplier], [Consumer], [Predicate]…), avec [Runnable], [Callable] et [Comparator], restent utilisables : quand une méthode Java attend une interface fonctionnelle, Kotlin y convertit automatiquement une lambda ou une référence (conversion SAM) ; ailleurs, on écrit la conversion : [Comparator { … }] ;
    • pour nommer un type de fonction, on dispose de l'alias [typealias] (un simple autre nom) et de la [fun interface] (un vrai type nouveau, implémentable par une lambda) ;
    • une fonction s'obtient par une expression lambda ([{ a, b -> a + b }], [{ it * it }], écrite hors des parenthèses quand elle est le dernier paramètre, quittée par [return@etiquette]), par une fonction anonyme, par un objet anonyme, ou par une référence ([::fonction], [objet::methode], [Classe::methode], [::Classe]). Deux références à la même fonction du même objet sont égales, deux lambdas ne le sont jamais ;
    • les lambdas capturent les variables qui les entourent, y compris les [var], qu'elles peuvent modifier (le compilateur les range dans des objets [Ref]) ; elles voient alors la valeur de la variable au moment de leur exécution, ce qui demande de l'attention dans les boucles et entre threads ;
    • des fonctions qui rendent des fonctions et des extensions sur les types fonctionnels ([puis], [et], [ou]…) composent de nouvelles fonctions ; [compareBy], [thenBy], [reversed] construisent des comparateurs ;
    • les fonctions [inline] recopient leur code et celui des lambdas à l'endroit de l'appel, sans objet ni conversion, et permettent le retour non local ; [noinline] et [crossinline] règlent les cas particuliers. Les fonctions de portée [let], [run], [with], [apply] et [also] en sont l'application la plus courante ;
    • on choisit un type fonctionnel pour un comportement court et ponctuel, une [fun interface] pour un type distinct ou une API utilisable depuis Java, une interface à plusieurs membres (ou une interface « métier ») pour un rôle de l'application ;
    • un événement se met en place avec le modèle des écouteurs : une classe [XxxEvent], un type d'écouteur (souvent un [typealias] de type fonctionnel), des méthodes [addXxxListener] / [removeXxxListener] et une liste de fonctions ([CopyOnWriteArrayList]) parcourue par une méthode [fireXxx]. Les propriétés déléguées [Delegates.observable] et [Delegates.vetoable] signalent ou filtrent les changements d'une propriété, et [PropertyChangeSupport] gère pour elles la liste des écouteurs ;
    • les opérations des collections (immédiates, [inline]) et des séquences (paresseuses) sont des fonctions d'ordre supérieur ; Kotlin n'a pas d'arbres d'expression, et Hibernate exprime ses requêtes en HQL ou avec l'API Criteria.

    Les lambdas reviendront dans tous les chapitres suivants : un thread exécute une lambda ([thread { … }]) et un [ExecutorService] un [Callable] (chapitre 8), une coroutine est lancée par [launch { … }] ou [async { … }] (chapitre 9), des fonctions d'extension de [ResultSet] recevront sous forme de lambda la transformation d'une ligne du résultat en objet (chapitre 10), et les services web de Spring Boot traitent les requêtes HTTP dans des méthodes que le cadriciel appelle comme des écouteurs (chapitre 13).
