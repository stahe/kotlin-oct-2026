    13. Services web

    13.1. Introduction

    Nous avons présenté au chapitre précédent plusieurs applications client-serveur TCP/IP. Dans la mesure où les clients et le serveur échangent des lignes de texte, ils peuvent être écrits dans n'importe quel langage. Le client doit simplement connaître le protocole de dialogue attendu par le serveur.

    Les services web sont, eux aussi, des applications serveur TCP/IP. Ils présentent les caractéristiques suivantes :

    • ils sont hébergés par des serveurs web et le protocole d'échange client-serveur est HTTP (HyperText Transfer Protocol), un protocole au-dessus de TCP/IP, que nous avons découvert au chapitre précédent ;
    • le service web a un protocole de dialogue standard, quel que soit le service assuré. Un service web offre divers services S1, S2…, Sn. Chacun d'eux attend des paramètres fournis par le client et rend à celui-ci un résultat. Pour chaque service, le client a besoin de savoir :
      • comment désigner le service Si ;
      • la liste des paramètres qu'il faut lui fournir et leur type ;
      • le type du résultat retourné par le service. Une fois ces éléments connus, le dialogue client-serveur suit le même format, quel que soit le service web interrogé. L'écriture des clients est ainsi normalisée ;
    • pour se protéger des attaques venant de l'Internet, beaucoup d'organisations n'ouvrent sur l'extérieur que certains ports de leurs serveurs : essentiellement les ports 80 (HTTP) et 443 (HTTPS) du service web. Tous les autres ports sont verrouillés. Aussi les applications client-serveur telles que celles du chapitre précédent sont-elles en général réservées au réseau privé de l'organisation (intranet). Loger un service au sein d'un serveur web le rend accessible à toute la communauté Internet ;
    • le service web peut être vu comme un objet distant : les services offerts deviennent alors des méthodes de cet objet. Un client peut utiliser cet objet distant comme s'il était local, au travers d'un objet intermédiaire appelé proxy (mandataire), qui cache toute la partie communication réseau. On construit ainsi un client indépendant de cette couche : si celle-ci vient à changer, le reste du client n'a pas à être modifié ;
    • comme pour les applications client-serveur TCP/IP du chapitre précédent, le client et le serveur peuvent être écrits dans des langages quelconques. Ils échangent des lignes de texte qui comportent deux parties : les entêtes nécessaires au protocole HTTP et le corps du message, dont le format est convenu entre le client et le serveur.

    13.1.1. Hier : SOAP et WSDL

    Dans les années 2000, les services web suivaient le plus souvent la norme SOAP (Simple Object Access Protocol). Le client envoyait une requête HTTP POST dont le corps était un document XML : une « enveloppe » contenant le nom de la méthode appelée et ses paramètres. Le serveur répondait par une autre enveloppe XML contenant le résultat. Chaque service était décrit par un document XML au format WSDL (Web Services Description Language), disponible à l'URL du service suivie de [?wsdl] : il listait les méthodes, leurs paramètres et leurs types. À partir de ce document, des outils généraient automatiquement le proxy du service.

    Sur la JVM, ces services s'écrivaient avec l'API JAX-WS : une classe annotée [@WebService], dont les méthodes publiques (éventuellement annotées [@WebMethod]) devenaient les méthodes du service ; l'outil [wsimport] générait le proxy client à partir du WSDL. JAX-WS faisait partie du JDK de Java 6 à Java 10 ; il en a été retiré par Java 11 (JEP 320) et vit désormais en dehors du JDK, sous le nom de Jakarta XML Web Services. Kotlin, apparu (en version 1.0) en 2016, n'a guère connu cette époque : on peut utiliser JAX-WS depuis Kotlin comme toute bibliothèque Java, mais les nouveaux services ne l'utilisent plus guère. Les raisons de cet abandon sont la lourdeur du XML et des enveloppes SOAP, la complexité des normes associées (WS-Security, WS-Addressing…) et la difficulté d'appeler ces services depuis un navigateur.

    13.1.2. Aujourd'hui : REST et JSON

    Les services web actuels suivent pour la plupart le style REST (REpresentational State Transfer) et échangent des documents JSON (JavaScript Object Notation, présenté au chapitre 5). Le style REST repose sur les principes suivants :

    • le service expose des ressources, chacune désignée par une URL : [/impot], [/clients/12], [/clients/12/commandes] ;
    • on agit sur ces ressources avec les méthodes (on dit aussi verbes) du protocole HTTP, chacune ayant une signification précise ;
    • le résultat de l'action est indiqué par le code de statut HTTP de la réponse ;
    • le corps des requêtes et des réponses est le plus souvent un document JSON, plus compact et plus simple que XML ;
    • le service est sans état : chaque requête contient toutes les informations nécessaires à son traitement ; le serveur ne mémorise rien d'une requête à l'autre pour un client donné.

    Les méthodes HTTP les plus utilisées sont les suivantes :

    Exemple

    lire une ressource ; les paramètres éventuels sont dans l'URL

    POST
    créer une ressource, ou demander un traitement ; les données sont dans le corps de la requête
    POST /clients
    PUT

    PUT /clients/12

    Les codes de statut, déjà rencontrés au chapitre précédent, prennent ici tout leur sens :

    Code
    Signification
    200 OK
    la requête a réussi ; le corps de la réponse contient le résultat

    204 No Content

    Un service REST n'a pas d'équivalent obligatoire du WSDL. Il est cependant d'usage de le décrire par un document OpenAPI (anciennement Swagger), au format JSON ou YAML, à partir duquel des outils peuvent générer de la documentation, des pages de test et des clients. Nous y reviendrons.

    Signalons enfin gRPC, conçu par Google : les méthodes du service et leurs messages sont décrits dans un fichier [.proto], à partir duquel des outils génèrent le serveur et le client, comme au temps du WSDL ; les messages sont codés dans un format binaire compact (Protocol Buffers) et transportés par HTTP/2. gRPC est très efficace et apprécié pour les échanges entre services d'une même organisation, mais il est mal adapté aux navigateurs. Il est disponible sur la JVM avec la bibliothèque [grpc-java], complétée pour Kotlin par [grpc-kotlin] (des fonctions [suspend] et des [Flow], chapitre 9), que nous n'utiliserons pas.

    13.1.3. Spring Boot et Spring MVC

    Pour écrire nos services web, nous utiliserons Spring Boot. Nous avons utilisé au chapitre 6 le conteneur d'injection de dépendances du Spring Framework. Ce cadriciel comprend aussi un module web, Spring MVC, qui associe une URL et une méthode HTTP à une fonction grâce à des annotations : [@RestController] sur la classe, [@GetMapping], [@PostMapping]… sur ses fonctions. Spring Boot (version 1.0 en 2014, version 4 en novembre 2025, avec Spring Framework 7) simplifie la mise en œuvre de Spring :

    • il configure automatiquement l'application d'après les bibliothèques présentes : si Spring MVC et Jackson sont là, il met en place tout ce qu'il faut pour un service web JSON, sans aucune ligne de configuration ;
    • il embarque le serveur web dans l'application : le serveur Tomcat (version 11) est une simple bibliothèque, démarrée par le programme principal. Il n'est donc pas nécessaire d'installer un serveur web ou un serveur d'applications séparé (Tomcat, GlassFish, WildFly…), dans lequel on déployait autrefois l'application sous la forme d'une archive [.war] ;
    • il fournit des starters, des dépendances qui regroupent tout ce qu'il faut pour un usage donné. Le starter [spring-boot-starter-webmvc] apporte Spring MVC, Tomcat, Jackson 3 (chapitre 5) et la journalisation (SLF4J et Logback) ;
    • il fournit une nomenclature (BOM, Bill Of Materials), qui fixe les versions de toutes ces bibliothèques, compatibles entre elles, et un greffon Gradle, [org.springframework.boot], qui lance l'application ([gradlew bootRun]) et la livre sous la forme d'un unique fichier [.jar] exécutable ([gradlew bootJar]).

    Spring est écrit en Java, mais il traite Kotlin comme un langage de premier rang depuis Spring Framework 5 (2017) : sa documentation donne ses exemples dans les deux langages, il comprend les types nullables de Kotlin, sait appeler les constructeurs primaires et leurs valeurs par défaut, et fournit des fonctions d'extension propres à Kotlin ([runApplication], [getBean<T>()], [registerBean<T>()] du chapitre 6…). Spring Boot n'est pas la seule solution : Jakarta EE (l'ancien Java EE) définit l'API standard JAX-RS (Jakarta RESTful Web Services), et des cadriciels comme Quarkus, Micronaut ou Helidon sont également très utilisés depuis Kotlin. Signalons surtout Ktor, le cadriciel web de JetBrains, écrit en Kotlin pour Kotlin : ses routes sont décrites par un langage dédié (DSL) plutôt que par des annotations, et ses traitements sont des fonctions [suspend] (chapitre 9). Spring Boot est cependant le plus répandu, et il prolonge naturellement ce que nous avons vu au chapitre 6.

    • lignes 3-7 : les trois greffons, sans version : celle-ci est fixée par le projet racine. Le greffon de Spring Boot ajoute au projet la tâche [bootRun], qui compile et lance l'application, et la tâche [bootJar], qui en fait un fichier [build/libs/WsHello-1.0.jar] contenant l'application et toutes ses dépendances, qu'on lance par [java -jar build/libs/WsHello-1.0.jar].     • ligne 19 : la nomenclature de Spring Boot 4.1.1 (la version du greffon). La fonction [platform] importe dans le projet les versions de plusieurs centaines de bibliothèques, choisies et testées ensemble par l'équipe de Spring Boot. C'est pourquoi les dépendances des lignes 21-23 n'ont pas de version. C'est l'équivalent du projet parent [spring-boot-starter-parent] d'un projet Maven ;
    • ligne 21 : le starter web. Il apporte Spring MVC (Spring Framework 7.0), le serveur Tomcat 11 embarqué, Jackson 3 et la journalisation ;
    • ligne 23 : la bibliothèque de réflexion de Kotlin. La réflexion de Java ([java.lang.reflect]) ne voit qu'une partie de ce qu'exprime le code Kotlin : elle ignore si un paramètre est de type nullable ([String?]), s'il a une valeur par défaut, quel est le constructeur primaire d'une classe. Spring lit ces informations grâce à [kotlin-reflect] (qui décode les métadonnées que le compilateur Kotlin range dans chaque fichier [.class]) : nous verrons qu'il s'en sert pour les paramètres facultatifs. Sa version est celle du greffon Kotlin ;
    • ligne 31 : l'option [-java-parameters] du compilateur, qui conserve dans les fichiers [.class] les noms des paramètres des fonctions. Spring en a besoin pour associer un paramètre de fonction ([nom]) au paramètre de même nom d'une URL, et Jackson pour associer les paramètres du constructeur d'une classe de données aux propriétés d'un document JSON (chapitre 5). Le greffon de Spring Boot active déjà cette option lorsqu'il voit le greffon Kotlin ; nous l'écrivons pour qu'elle soit visible ;
    • lignes 35-38 : les programmes lancés par Gradle écrivent leurs sorties en UTF-8, pour que les caractères accentués s'affichent correctement sous Windows (chapitre 2).

    • ligne 7 : l'annotation [@SpringBootApplication] réunit trois annotations : [@Configuration] (la classe peut définir des beans, comme au chapitre 6), [@EnableAutoConfiguration] (la configuration automatique d'après les bibliothèques présentes) et [@ComponentScan] (Spring recherche les classes annotées, contrôleurs, configurations…, dans le paquetage de cette classe et ses sous-paquetages) ;

Ici, ce n'est pas indispensable : nous avons vérifié que l'application démarre aussi lorsque la classe reste finale, car Spring n'a pas à dériver une classe de configuration qui ne définit aucun bean. Mais une classe de configuration qui définit des beans par des fonctions [@Bean], comme celle du service de calcul de l'impôt, provoquerait l'erreur [@Configuration class '...' may not be final] rencontrée au chapitre 6 : le greffon évite d'avoir à y penser ;
    • lignes 10-12 : le programme principal est une fonction de haut niveau, compilée dans la classe [WsHelloApplicationKt]. La fonction [runApplication<WsHelloApplication>(*args)], une fonction d'extension de Spring Boot écrite pour Kotlin, remplace l'appel Java [SpringApplication.run(WsHelloApplication.class, args)] : le type de la classe de configuration est passé comme argument de type ([reified], chapitre 4), et l'opérateur [*] (spread) transmet les éléments du tableau [args] au paramètre [vararg] de la fonction (chapitre 3). [runApplication] lit la configuration (fichier [application.properties], variables d'environnement, arguments de la ligne de commande), crée le conteneur Spring et ses beans, démarre le serveur Tomcat, puis rend la main. Le programme ne s'arrête pas pour autant : les threads de Tomcat attendent les requêtes jusqu'à l'arrêt de l'application (Ctrl-C).

// le service web WsHello : chaque fonction annotée traite une URL
@RestController
class HelloController {

    @GetMapping("/")
    fun accueil() = "Service web WsHello : essayez /hello/{nom} ou /salutation/{nom}"

    // le segment {nom} de l'URL est passé au paramètre [nom] de la fonction
    // une chaîne de caractères est rendue telle quelle (text/plain)
    @GetMapping("/hello/{nom}")
    fun hello(@PathVariable nom: String) = "Bonjour Mme $nom"

    @GetMapping("/salutation/{nom}")

    • ligne 8 : l'annotation [@RestController] fait de la classe un contrôleur : Spring en crée une instance unique (un singleton) au démarrage, et lui confie les requêtes HTTP dont l'URL correspond à l'une de ses fonctions. Le résultat de chaque fonction est envoyé tel quel au client, dans le corps de la réponse ;

import java.io.IOException
import java.net.ConnectException
import java.net.URI
import java.net.URLEncoder
import java.net.http.HttpClient
import java.net.http.HttpRequest
import java.net.http.HttpResponse
import tools.jackson.databind.json.JsonMapper

// la réponse JSON du service : mêmes noms de propriétés que côté serveur
data class Salutation(val nom: String, val message: String)

// client console du service web WsHello
fun main(args: Array<String>) {
    // l'URL du service peut être passée en argument
    val urlService = URI.create(args.firstOrNull() ?: "http://localhost:5100/")
    // le convertisseur JSON <-> objets de Jackson
    val mapper = JsonMapper.builder().build()

    // un unique client HTTP pour toute la durée du programme, fermé à la fin par [use]
    HttpClient.newHttpClient().use { client ->
        while (true) {
            // le nom de la dame
            print("Nom de la dame (rien pour arrêter) : ")
            val nom = readlnOrNull()?.trim() ?: ""
            if (nom.isEmpty()) {
                break
            }
            try {
                // le nom est placé dans le chemin de l'URL : il doit y être encodé
                val nomEncode = URLEncoder.encode(nom, Charsets.UTF_8).replace("+", "%20")
                // 1 - réponse texte
                val texte = client.get(urlService.resolve("hello/$nomEncode"))
                println("[texte] $texte")
                // 2 - réponse JSON, désérialisée en un objet Salutation
                val json = client.get(urlService.resolve("salutation/$nomEncode"))
                val salutation = mapper.readValue(json, Salutation::class.java)
                println("[JSON]  $salutation")
            } catch (_: ConnectException) {
                // aucun service n'écoute à cette adresse (l'exception n'a pas de message)
                println("Erreur : ConnectException : connexion refusée ($urlService)")
            } catch (e: IOException) {
                // le service a répondu par une erreur, ou la communication a échoué
                println("Erreur : ${e::class.simpleName} : ${e.message}")
            }
        }
    }
}

// une requête GET dont le corps de la réponse est rendu sous forme de chaîne
// (une fonction d'extension de la classe HttpClient)
fun HttpClient.get(url: URI): String {
    val requete = HttpRequest.newBuilder(url).GET().build()
    val reponse = send(requete, HttpResponse.BodyHandlers.ofString())
    // un code de statut autre que 2xx est une erreur
    if (reponse.statusCode() / 100 != 2) {
        throw IOException("le service a répondu ${reponse.statusCode()} pour $url")
    }
    return reponse.body()
}

    • ligne 13 : la réponse JSON du service sera désérialisée en un objet [Salutation]. Le client n'a pas accès au type [Salutation] du serveur : il déclare le sien, une classe de données avec les mêmes noms de propriétés. Un client ne partage pas le code du serveur, seulement le format des documents échangés ;
    • ligne 18 : l'URL du service est passée en argument ou, à défaut, vaut [http://localhost:5100/] : si l'adresse du service change, le client n'a pas à être recompilé. [firstOrNull()] rend le premier élément du tableau, ou [null] s'il est vide, et l'opérateur Elvis [?:] remplace ce [null] par l'URL par défaut ;
    • ligne 20 : le convertisseur JSON de Jackson 3 (chapitre 5) ;
    • ligne 23 : un unique [HttpClient] pour tout le programme. Il gère un ensemble de connexions réutilisables et doit être partagé, et non recréé à chaque requête. Depuis Java 21, [HttpClient] implémente [AutoCloseable] : la fonction [use] de Kotlin (chapitre 3) le ferme à la fin du bloc, même en cas d'exception ;
    • lignes 26-27 : la question, puis la lecture de la réponse ; en fin de flux, [readlnOrNull] rend [null], que l'opérateur Elvis transforme en chaîne vide ;
    • ligne 33 : le nom saisi devient un segment de l'URL : il faut coder les caractères qui n'y sont pas autorisés. [URLEncoder.encode] code le é en [%C3%A9], mais il est fait pour les paramètres de formulaires, où l'espace est codé [+]. Dans le chemin d'une URL, l'espace doit être codé [%20] : on remplace donc les [+] (un vrai [+] saisi est codé [%2B] et n'est pas concerné). [Charsets.UTF_8] est la constante de Kotlin pour le jeu de caractères UTF-8 (celle de Java, [StandardCharsets.UTF_8], convient aussi) ;
    • ligne 35 : la méthode [resolve] de la classe [URI] construit une URL à partir de l'URL de base et d'une URL relative. Attention : l'URL de base doit se terminer par [/] pour que [hello/...] lui soit ajouté. La fonction [get] est appelée comme une méthode de [HttpClient] : c'est une fonction d'extension, définie plus bas ;
    • lignes 38-39 : la réponse JSON est désérialisée en un objet [Salutation] par la méthode [readValue] de Jackson ;
    • lignes 41-43 : l'exception [ConnectException] est lancée lorsque la connexion au service est impossible, par exemple lorsque aucun service n'écoute à l'adresse indiquée. Elle n'a pas de message : nous en construisons un. Le nom [_] indique que l'exception n'est pas utilisée. Ce [catch] doit précéder celui de la ligne 44, car [ConnectException] dérive de [IOException] ;
    • lignes 44-46 : les autres erreurs de communication, et les réponses d'erreur du service (voir ligne 59) ;
    • lignes 54-61 : une requête GET, dont le corps de la réponse est rendu sous forme de chaîne. Nous l'avons écrite comme une fonction d'extension de la classe [HttpClient] (chapitre 4) : dans son corps, [send] désigne la méthode [send] du client sur lequel elle est appelée ([this]). En Java, c'était une méthode statique qui recevait le client en paramètre ;
    • ligne 55 : la requête est construite par un constructeur (builder) : l'URL, la méthode HTTP, puis [build] ;
    • ligne 56 : la méthode [send] envoie la requête et attend la réponse. Son second paramètre, un [BodyHandler], indique ce qu'il faut faire du corps de la réponse : [ofString] le lit entièrement dans une chaîne, décodée selon le jeu de caractères indiqué par l'entête [Content-Type] (UTF-8 par défaut).     13.2.4. La description du service : OpenAPI

    Le WSDL décrivait un service SOAP de façon normalisée. Son équivalent actuel est le document OpenAPI. Pour Spring Boot, la bibliothèque [springdoc-openapi] (dépendance [org.springdoc:springdoc-openapi-starter-webmvc-ui]) le produit sans aucune ligne de code : elle examine les contrôleurs et leurs annotations au démarrage et publie le document à l'URL [/v3/api-docs], ainsi qu'une page de test interactive, Swagger UI, à l'URL [/swagger-ui.html]. Le document décrit chaque route : son URL, sa méthode HTTP, ses paramètres et leur type, le schéma JSON de ses réponses. Avec Kotlin, elle tient compte de la nullabilité des types : une propriété de type [String] est déclarée obligatoire, une propriété de type [String?] facultative. Des générateurs comme OpenAPI Generator en tirent un client typé dans divers langages (Kotlin compris), exactement comme [wsimport] le faisait avec le WSDL. Cette bibliothèque ne fait pas partie de Spring Boot, et nous ne l'utiliserons pas dans ce chapitre.

import org.springframework.http.HttpStatus
import org.springframework.http.ProblemDetail
import org.springframework.http.ResponseEntity
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.PathVariable
import org.springframework.web.bind.annotation.PostMapping
import org.springframework.web.bind.annotation.RequestBody
import org.springframework.web.bind.annotation.RequestParam
import org.springframework.web.bind.annotation.RestController

// le service web WsOperations : les quatre opérations arithmétiques
@RestController
class OperationsController {

    // GET /ajouter?a=1.5&b=2 (de même pour soustraire, multiplier, diviser)
    // [operation] vient du chemin de l'URL, [a] et [b] de sa chaîne de requête
    // a et b sont de type String? : Spring les considère donc comme facultatifs
    @GetMapping("/{operation}")
    fun calculerGet(
        @PathVariable operation: String,
        @RequestParam a: String?,
        @RequestParam b: String?,
    ): ResponseEntity<*> = calculer(operation, lireNombre(a), lireNombre(b))

    // POST /calcul avec un corps JSON : {"operation":"ajouter","a":1.5,"b":2}
    // le corps JSON est désérialisé dans le paramètre [demande]
    @PostMapping("/calcul")
    fun calculerPost(@RequestBody demande: DemandeCalcul): ResponseEntity<*> =
        calculer(demande.operation, demande.a, demande.b)

    // un nombre écrit avec un point décimal, null s'il est absent ou incorrect
    // (NaN et les infinis sont refusés)
    private fun lireNombre(texte: String?): Double? = texte?.toDoubleOrNull()?.takeIf { it.isFinite() }

    // le calcul commun aux deux méthodes HTTP
    private fun calculer(operation: String?, a: Double?, b: Double?): ResponseEntity<*> {
        // le nom de l'opération, en minuscules
        val nom = operation?.lowercase() ?: ""
        // l'opération demandée, null si elle est inconnue
        val calcul: ((Double, Double) -> Double)? = when (nom) {
            "ajouter" -> { x, y -> x + y }
            "soustraire" -> { x, y -> x - y }
            "multiplier" -> { x, y -> x * y }
            "diviser" -> { x, y -> x / y }
            else -> null
        }
        // vérification des paramètres : on accumule les erreurs
        if (calcul == null || a == null || b == null) {
            val erreurs = buildMap {
                if (calcul == null) {
                    put("operation", listOf(
                        "Opération [$nom] inconnue : utilisez ajouter, soustraire, multiplier ou diviser"))
                }
                if (a == null) put("a", listOf("Le nombre a est absent ou incorrect"))
                if (b == null) put("b", listOf("Le nombre b est absent ou incorrect"))
            }
            // réponse 400 avec la liste des erreurs
            val probleme = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST).apply {
                title = "Paramètres incorrects"
                setProperty("errors", erreurs)
            }
            return ResponseEntity.badRequest().body(probleme)
        }
        // ici, le compilateur sait que calcul, a et b ne sont pas null (transtypage intelligent)
        // la division par zéro est refusée : réponse 400
        if (nom == "diviser" && b == 0.0) {
            val probleme = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "Le nombre b doit être non nul pour une division"
            ).apply { title = "Division par zéro" }
            return ResponseEntity.badRequest().body(probleme)
        }
        // réponse 200 avec le résultat en JSON
        return ResponseEntity.ok(ResultatCalcul(nom, a, b, calcul(a, b)))
    }

    // la demande de calcul (corps de la requête POST) : les propriétés absentes du JSON valent null
    data class DemandeCalcul(val operation: String?, val a: Double?, val b: Double?)

    // le résultat d'un calcul (corps de la réponse)
    data class ResultatCalcul(val operation: String, val a: Double, val b: Double, val resultat: Double)
}

    Commentaires :

    • lignes 20-25 : la requête GET. Le paramètre [operation] de la fonction est lié à la variable de route [{operation}] ([@PathVariable]). Les paramètres [a] et [b], annotés [@RequestParam], sont liés aux paramètres de même nom de la chaîne de requête ([?a=1.5&b=2]). Ils sont facultatifs : un paramètre absent vaut [null]. En Java, il fallait l'écrire ([@RequestParam(required = false) String a]) ; en Kotlin, il suffit de déclarer le paramètre nullable, [String?] : Spring lit, grâce à [kotlin-reflect], la nullabilité du type et en déduit que le paramètre est facultatif. Inversement, un paramètre de type non nullable ([String]) est obligatoire : Spring rejetterait par une réponse 400 une requête à laquelle il manquerait. Le type déclaré dit donc à la fois au compilateur et à Spring ce qui peut manquer ;
    • lignes 23-24 : [a] et [b] sont déclarés de type [String?]. Nous aurions pu les déclarer de type [Double?] : Spring aurait alors fait lui-même la conversion, et rejeté une valeur incorrecte par une réponse 400 au message générique. En les recevant sous forme de chaînes, nous gardons la maîtrise des messages d'erreur ;
    • ligne 25 : la fonction a un corps d'expression. Son type de retour, [ResponseEntity<*>], est écrit explicitement : le type étoilé [*] (chapitre 4) désigne une réponse dont le type du corps n'est pas précisé, l'équivalent du [ResponseEntity<?>] de Java ;
    • lignes 29-31 : la requête POST. Le paramètre [demande], annoté [@RequestBody], est construit par Jackson à partir du corps JSON de la requête. Les propriétés de la classe [DemandeCalcul] sont nullables (ligne 79) : une propriété absente du document JSON vaut alors [null], ce qui permet de la détecter ;
    • ligne 35 : la conversion d'une chaîne en nombre, [null] si elle échoue, écrite en une expression. L'opérateur [?.] propage le [null] d'une chaîne absente ; la fonction [toDoubleOrNull] de Kotlin rend [null] au lieu de lancer une exception ; la fonction [takeIf] rend son objet si la condition est vraie, [null] sinon : elle refuse ici les valeurs [NaN] et les infinis, que [toDoubleOrNull] accepte (textes [NaN] et [Infinity]). Dans une URL comme en JSON, les nombres s'écrivent avec un point décimal : [toDoubleOrNull], qui ne dépend pas de la langue du système, est donc le bon outil (et non [NumberFormat], qui attendrait une virgule sur un serveur français, chapitre 5). En Java, il fallait un bloc [try]/[catch] autour de [Double.parseDouble] ;
    • ligne 40 : le nom de l'opération, en minuscules. La fonction [lowercase] de Kotlin fait la conversion indépendamment de la langue du système (elle utilise [Locale.ROOT], qu'il fallait préciser en Java) ;
    • lignes 42-47 : l'opération demandée est représentée par une fonction de type [(Double, Double) -> Double] (chapitre 7), nullable : [((Double, Double) -> Double)?]. Une expression [when] choisit la lambda correspondant à l'opération, [null] pour une opération inconnue. Le type déclaré de [calcul] permet au compilateur d'inférer le type des paramètres [x] et [y] des lambdas ;
    • lignes 50-64 : on vérifie les trois paramètres. Si l'un d'eux est incorrect, on construit la liste des erreurs : un dictionnaire qui associe à chaque paramètre la liste de ses messages d'erreur. La fonction [buildMap], de la même famille que [buildString] et [buildList] (chapitre 5), crée un dictionnaire modifiable, l'offre comme receveur ([this]) au bloc, où [put] le remplit, puis le rend en lecture seule ; il conserve l'ordre d'insertion ;
    • lignes 60-64 : la réponse 400. La classe [ProblemDetail] de Spring représente un document « Problem Details » : [forStatus] le crée avec un code de statut. La fonction [apply] (chapitre 4) exécute le bloc avec l'objet créé comme receveur, puis rend cet objet : on y fixe son titre en écrivant la propriété [title] (Kotlin voit les méthodes Java [getTitle]/[setTitle] comme une propriété) et on lui ajoute par [setProperty] une propriété quelconque, ici [errors], la liste des erreurs. La classe [ResponseEntity] représente une réponse HTTP complète : code de statut, entêtes et corps. [ResponseEntity.badRequest()] prépare une réponse 400 et [body] lui donne son corps ;
    • ligne 66 : après le [return] de la ligne 64, le compilateur sait que [calcul], [a] et [b] ne sont pas [null] : ce sont des variables locales (ou des paramètres) qui ne peuvent plus changer. Il les traite désormais comme des valeurs de types non nullables [(Double, Double) -> Double] et [Double] : c'est le transtypage intelligent (smart cast) du chapitre 3. Nous avons organisé le test pour en profiter : le Java testait séparément chaque paramètre et accumulait les erreurs dans un dictionnaire, puis testait si le dictionnaire était vide ; or ce dernier test ne dirait rien au compilateur sur [a] et [b] ;
    • lignes 68-72 : la division par zéro est refusée par une réponse 400, dont le document comporte cette fois un détail ([forStatusAndDetail]). Ce refus est nécessaire : la division d'un [Double] par zéro ne lance pas d'exception mais donne l'infini ([Double.POSITIVE_INFINITY]), qu'un document JSON ne sait pas représenter (Jackson l'écrirait sous forme de chaîne, ["Infinity"]). Le test [b == 0.0] compare deux [Double] : le littéral doit être [0.0], car Kotlin refuse de comparer un [Double] et un [Int] ([b == 0] provoque l'erreur de compilation [operator '==' cannot be applied to 'Double' and 'Int']) ;
    • ligne 75 : la réponse 200, dont le corps est l'objet [ResultatCalcul] sérialisé en JSON. [calcul(a, b)] appelle la fonction choisie plus haut ;
    • lignes 79-82 : les deux types échangés avec les clients. Ces objets, qui ne servent qu'à transporter des données entre deux applications, sont appelés DTO (Data Transfer Object). Les classes de données sont parfaites pour cet usage. Les propriétés de [DemandeCalcul], reçue du client, sont nullables ; celles de [ResultatCalcul], produite par le service, ne le sont pas.

    Les deux fonctions du contrôleur rendent le type [ResponseEntity<*>] : une réponse dont le corps peut être de n'importe quel type, ici un [ResultatCalcul] ou un [ProblemDetail]. Spring examine le type réel du corps pour le sérialiser ; il donne au document le type [application/json], ou [application/problem+json] pour un [ProblemDetail].

data class ResultatCalcul(val operation: String, val a: Double, val b: Double, val resultat: Double)

    val title: String?,
    val detail: String?,
    val status: Int?,

// les nombres sont saisis et affichés dans la culture courante (fr-FR : virgule décimale)
private val FORMAT = NumberFormat.getInstance()

// client console du service web WsOperations
fun main(args: Array<String>) {
    val urlService = URI.create(args.firstOrNull() ?: "http://localhost:5110/")
    // le convertisseur JSON ; Jackson 3 ignore les propriétés JSON inconnues (instance...)
    val mapper = JsonMapper.builder().build()

    HttpClient.newHttpClient().use { client ->
        while (true) {
            // saisie de l'opération et des deux nombres (virgule décimale française)
            print("Opération a b (ex. : ajouter 1,5 2), rien pour arrêter : ")
            val saisie = readlnOrNull()?.trim() ?: ""
            if (saisie.isEmpty()) {
                break
            }
            val champs = saisie.split(Regex("""\s+"""))
            if (champs.size != 3) {
                println("Il faut trois éléments : opération a b")
                continue
            }
            // vérification locale des deux nombres, avant tout appel au service
            val (operation, texteA, texteB) = champs
            val a = lireNombre(texteA)
            if (a == null) {
                println("Nombre a erroné...")
            }
            val b = lireNombre(texteB)
            if (b == null) {
                println("Nombre b erroné...")
            }
            if (a == null || b == null) {
                continue
            }
            val calcul = "$operation(${FORMAT.format(a)} ; ${FORMAT.format(b)})"

            // 1 - requête GET : dans l'URL, les nombres sont écrits avec un point décimal
            val url = "${URLEncoder.encode(operation, Charsets.UTF_8)}?a=$a&b=$b"
            try {
                val requete = HttpRequest.newBuilder(urlService.resolve(url)).GET().build()
                val reponse = client.send(requete, BodyHandlers.ofString())
                if (reponse.statusCode() == 200) {
                    val resultat = mapper.readValue(reponse.body(), ResultatCalcul::class.java)
                    println("[GET $url] $calcul = ${FORMAT.format(resultat.resultat)}")
                } else {
                    // échec : on affiche le code de statut et le document reçu, tel quel
                    println("[GET $url] erreur ${reponse.statusCode()} : ${reponse.body()}")
                }
            } catch (e: IOException) {
                // le service est injoignable
                println("[GET $url] erreur : $e")
            }

            // 2 - requête POST : la demande est envoyée en JSON dans le corps de la requête
            try {
                val json = mapper.writeValueAsString(DemandeCalcul(operation, a, b))
                val requete = HttpRequest.newBuilder(urlService.resolve("calcul"))
                    .header("Content-Type", "application/json")
                    .POST(HttpRequest.BodyPublishers.ofString(json))
                    .build()
                val reponse = client.send(requete, BodyHandlers.ofString())
                if (reponse.statusCode() == 200) {
                    // succès : le corps contient le résultat
                    val resultat = mapper.readValue(reponse.body(), ResultatCalcul::class.java)
                    println("[POST calcul] $calcul = ${FORMAT.format(resultat.resultat)}")
                } else {
                    // échec : le corps contient la description du problème
                    val probleme = mapper.readValue(reponse.body(), Probleme::class.java)
                    println("[POST calcul] erreur ${reponse.statusCode()} : ${probleme.title}")
                    probleme.detail?.let { println("  $it") }
                    probleme.errors?.forEach { (parametre, messages) ->
                        println("  $parametre : ${messages.joinToString(" ; ")}")
                    }
                }
            } catch (e: IOException) {
                // le service est injoignable
                println("[POST calcul] erreur : $e")
            }
        }
    }
}

// un nombre saisi dans la culture courante, null si la saisie n'en est pas un
fun lireNombre(texte: String): Double? {
    val position = ParsePosition(0)
    val nombre = FORMAT.parse(texte, position)
    // la saisie doit avoir été lue en entier : « 2,5x » est refusé
    return if (nombre == null || position.index != texte.length) null else nombre.toDouble()
}

Un contrôleur ne doit jamais ranger dans ses propriétés des données propres à une requête. Signalons enfin que la propriété [spring.threads.virtual.enabled=true] fait traiter chaque requête par un thread virtuel (Java 21, chapitre 8) au lieu d'un thread du pool de Tomcat : le service peut alors traiter un très grand nombre de requêtes simultanées qui attendent des entrées-sorties. Spring MVC accepte aussi des fonctions de contrôleur [suspend] (chapitre 9) ; elles prennent tout leur sens avec Spring WebFlux, la variante non bloquante de Spring MVC, où une requête n'occupe aucun thread pendant ses attentes.

    package impots.client

import impots.entites.ImpotException
import impots.metier.IImpotMetier
import java.io.IOException
import java.net.URI
import java.net.http.HttpClient
import java.net.http.HttpRequest
import java.net.http.HttpResponse
import tools.jackson.databind.json.JsonMapper

// la couche [metier] côté client : un proxy du service web de calcul de l'impôt
// elle implémente la même interface que la couche [metier] locale de la version 5
class ImpotMetierHttp(private val client: HttpClient, urlService: URI) : IImpotMetier {

    // les objets échangés avec le service web
    private data class DemandeImpot(val marie: Boolean, val enfants: Int, val salaire: Int)

    private data class ReponseImpot(val impot: Int)

    // l'URL de la méthode POST /impot, le convertisseur JSON
    private val urlImpot = urlService.resolve("impot")
    private val mapper = JsonMapper.builder().build()

    override fun calculerImpot(marie: Boolean, nbEnfants: Int, salaire: Int): Int {
        // la requête POST /impot, avec la demande en JSON dans son corps
        val json = mapper.writeValueAsString(DemandeImpot(marie, nbEnfants, salaire))
        val requete = HttpRequest.newBuilder(urlImpot)
            .header("Content-Type", "application/json")
            .POST(HttpRequest.BodyPublishers.ofString(json))
            .build()
        val reponse = try {
            // envoi synchrone : la fonction attend la réponse
            client.send(requete, HttpResponse.BodyHandlers.ofString())
        } catch (e: IOException) {
            // le service est injoignable
            throw ImpotException("Le service web $urlImpot est injoignable", e)
        } catch (e: InterruptedException) {
            // le thread a été interrompu pendant l'attente : on le signale à nouveau
            Thread.currentThread().interrupt()
            throw ImpotException("Le calcul de l'impôt a été interrompu", e)
        }
        // le service a-t-il accepté la demande ?
        if (reponse.statusCode() != 200) {
            throw ImpotException(
                "Le service web a répondu ${reponse.statusCode()} : ${reponse.body()}",
                code = reponse.statusCode(),
            )
        }
        // la réponse JSON {"impot":4282}
        return mapper.readValue(reponse.body(), ReponseImpot::class.java).impot
    }
}

    Commentaires :

    • ligne 14 : la classe implémente l'interface [IImpotMetier] de la version 5. Elle reçoit par son constructeur primaire le client HTTP, dont elle fait une propriété privée ([private val client]), et l'URL du service, simple paramètre du constructeur ;
    • lignes 17-19 : les DTO, déclarés à l'intérieur de la classe ([private]) car personne d'autre ne les utilise ;
    • lignes 22-23 : l'URL de la fonction [POST /impot], calculée à partir de celle du service lors de l'initialisation de la propriété (le paramètre [urlService] du constructeur primaire est utilisable dans les initialiseurs des propriétés), et le convertisseur JSON ;
    • lignes 27-31 : la requête [POST /impot], avec la demande sérialisée en JSON dans son corps ;
    • lignes 32-34 : la requête est envoyée de façon synchrone : la méthode [send] attend la réponse, ce qui convient à la fonction [calculerImpot] de l'interface, elle-même synchrone (elle rend un [Int]). [try] est une expression en Kotlin (chapitre 3) : sa valeur, ici la réponse, est celle du bloc [try] si tout va bien ; les blocs [catch] se terminant par un [throw] (de type [Nothing]), la variable [reponse] est de type [HttpResponse<String>] et peut être un [val], là où le Java devait la déclarer avant le [try] ;
    • lignes 35-37 : [send] lance une [IOException] si le service est injoignable. Elle est encapsulée dans une [ImpotException], l'exception de l'application [Impots]. Kotlin ne l'imposait pas (il n'a pas d'exceptions contrôlées), mais c'est la bonne pratique de l'architecture en couches : la couche [ui] ne connaît que les exceptions de l'application, pas celles de la technique de communication utilisée par la couche [metier] ;
    • lignes 38-41 : de même pour l'[InterruptedException], lancée si le thread est interrompu pendant l'attente. Le fait de l'attraper efface l'indicateur d'interruption du thread : la bonne pratique (chapitre 8) est de le rétablir, par [Thread.currentThread().interrupt()], pour que le code appelant puisse savoir que le thread a été interrompu ;
    • lignes 44-47 : une réponse d'erreur est transformée en [ImpotException], dont le code est le code de statut HTTP. Le constructeur de [ImpotException] (chapitre 6) a un paramètre [cause] avec une valeur par défaut ; pour fixer le code sans donner de cause, on nomme l'argument : [code = reponse.statusCode()] ;
    • ligne 51 : la réponse JSON [{"impot":4282}] est désérialisée et le montant de l'impôt est rendu.

    Avec un service SOAP, l'outil [wsimport] générait un proxy, et une classe semblable à celle-ci implémentait [IImpotMetier] en lui déléguant le calcul : aujourd'hui, nous écrivons nous-mêmes les quelques dizaines de lignes du proxy.

    La fonction [calculerImpot] de l'interface [IImpotMetier] étant synchrone, nous avons utilisé la méthode synchrone [send] de [HttpClient]. Celui-ci offre aussi une méthode asynchrone, [sendAsync], qui rend immédiatement un [CompletableFuture<HttpResponse<T>>]. En Kotlin, on l'utiliserait depuis une fonction [suspend], en attendant le résultat par la fonction d'extension [await()] de kotlinx-coroutines (chapitre 9) : [suspend fun calculerImpot(marie: Boolean, nbEnfants: Int, salaire: Int): Int]. Cela obligerait à modifier l'interface [IImpotMetier], ses implémentations et la couche [ui]. Nous ne l'avons pas fait, pour garder intactes les couches de la version 5. Avec les threads virtuels (Java 21), le code synchrone redevient d'ailleurs une façon raisonnable d'écrire des programmes qui attendent beaucoup d'entrées-sorties : un thread virtuel bloqué par [send] ne bloque pas de thread du système.

Pour accepter d'autres origines, un contrôleur Spring peut être annoté [@CrossOrigin(origins = ["http://localhost:5000"])] (en Kotlin, un argument de type tableau s'écrit entre crochets dans une annotation) ; une configuration globale est aussi possible (fonction [addCorsMappings] de l'interface [WebMvcConfigurer]). Les clients qui ne sont pas des navigateurs ([curl], nos clients console) ne sont pas concernés par CORS.

    Pour des interfaces web plus riches produites par le serveur, Spring MVC propose aussi des contrôleurs qui rendent des pages HTML construites à partir de modèles (Thymeleaf, par exemple), qui ne relèvent pas de ce cours. Kotlin offre de plus une solution qui lui est propre : Kotlin/JS et Kotlin/Wasm compilent du code Kotlin pour le navigateur, ce qui permet d'écrire le client web dans le même langage que le service, en partageant au besoin les classes de données des DTO (projets Kotlin Multiplatform).

    13.7. Compléments

    13.7.1. Le type des réponses et la gestion des erreurs

    Le service [WsOperations] rend des objets [ResponseEntity<*>] : on ne sait pas, à la lecture de la signature de ses fonctions, quelles réponses elles peuvent produire, et le compilateur ne vérifie rien. Le service [WsImpot] rend le type précis de sa réponse en cas de succès, [ReponseImpot], et signale les erreurs par des exceptions, transformées en réponses par un gestionnaire [@ExceptionHandler]. C'est la forme la plus courante avec Spring : le code des fonctions ne traite que le cas normal, et les outils (le générateur de documents OpenAPI en particulier) connaissent le schéma JSON de la réponse sans qu'on le leur dise. Un test unitaire peut aussi appeler directement une fonction du contrôleur et examiner son résultat, sans passer par HTTP. [ResponseEntity<T>], avec un type précis, reste utile lorsqu'il faut choisir le code de statut ou ajouter des entêtes, par exemple pour une réponse 201 (Created) accompagnée de son entête [Location] : [ResponseEntity.created(uri).body(client)].

    Un gestionnaire [@ExceptionHandler] placé dans un contrôleur ne traite que les exceptions de ce contrôleur. Pour traiter les exceptions de tous les contrôleurs d'une application, on place les gestionnaires dans une classe annotée [@RestControllerAdvice]. Spring fournit aussi la classe [ErrorResponseException], une exception qui porte directement un [ProblemDetail] et produit la réponse correspondante sans gestionnaire, et la classe [ResponseEntityExceptionHandler], dont on peut hériter pour personnaliser les réponses aux erreurs détectées par Spring MVC lui-même (document JSON illisible, type de document refusé…).

    En Kotlin, on peut aussi représenter le résultat d'une opération par une classe scellée (chapitre 4) : [sealed interface Resultat], avec une classe de données pour le succès et une autre pour l'échec. Une expression [when] exhaustive transforme alors chaque cas en réponse HTTP, et le compilateur vérifie qu'aucun cas n'est oublié. C'est une alternative aux exceptions, appréciée des développeurs Kotlin, qui garde visibles dans les types les échecs possibles d'une opération.

    13.7.2. Un préfixe commun aux routes

    Lorsque plusieurs routes partagent un préfixe, on l'indique une fois pour toutes par l'annotation [@RequestMapping] placée sur la classe du contrôleur. Par exemple, avec [@RequestMapping("/api/operations")] sur la classe [OperationsController], les routes deviennent [GET /api/operations/ajouter?a=1&b=2] et [POST /api/operations/calcul], sans autre modification. C'est aussi une façon simple de gérer les versions d'un service ([/api/v1/...], [/api/v2/...]).

    13.7.3. Intercepteurs et validation

    Nos services vérifient eux-mêmes leurs paramètres. Spring propose deux mécanismes pour sortir ce code des contrôleurs :

    • les intercepteurs : une classe qui implémente l'interface [HandlerInterceptor], enregistrée par la fonction [addInterceptors] de [WebMvcConfigurer], est exécutée avant et après les fonctions des contrôleurs ; elle peut examiner la requête et répondre elle-même, sans appeler le contrôleur. On les utilise pour la journalisation, la mesure des temps de réponse, l'authentification… Les filtres de servlet ([jakarta.servlet.Filter]) jouent le même rôle à un niveau plus bas ;
    • la validation : avec le starter [spring-boot-starter-validation] (qui apporte Hibernate Validator, l'implémentation de référence de l'API Jakarta Validation), les propriétés d'un DTO peuvent être annotées par des contraintes : [data class DemandeImpot(@NotNull val marie: Boolean?, @NotNull @Min(0) val enfants: Int?, @NotNull @Min(0) val salaire: Int?)]. Avec Kotlin 2.4, une annotation placée sur une propriété déclarée dans le constructeur primaire s'applique à la fois au paramètre du constructeur et au champ de la propriété, que lit le validateur (nous l'avons vérifié par réflexion sur une annotation de notre cru). Les versions antérieures de Kotlin ne l'appliquaient qu'au paramètre : il fallait préciser la cible de l'annotation, [@field:NotNull], forme que l'on rencontre encore dans beaucoup d'exemples. Un paramètre [@Valid @RequestBody demande: DemandeImpot] est alors vérifié avant l'appel de la fonction, et une demande incorrecte est rejetée par une réponse 400 « Problem Details », comme celles que nous avons construites.

    13.7.4. Hébergement

    Nos services sont exécutés par [gradlew bootRun], ce qui convient au développement. En production :

    • l'application est d'abord empaquetée par [gradlew bootJar] : le greffon de Spring Boot produit un unique fichier [.jar] « exécutable », qui contient l'application, ses dépendances (dont la bibliothèque standard de Kotlin) et le serveur Tomcat. Il suffit de le copier sur le serveur et de le lancer par [java -jar WsImpot-9.0.jar], la configuration pouvant être modifiée par des arguments ([--server.port=80]), des variables d'environnement ou un fichier [application.properties] placé à côté du [.jar]. Pour la JVM, une application Kotlin est une application Java comme une autre ;
    • Tomcat peut être exposé directement sur l'Internet, mais il est souvent placé derrière un proxy inverse (nginx ou Apache sous Linux, IIS sous Windows) qui reçoit les requêtes HTTPS, gère les certificats et répartit la charge entre plusieurs instances de l'application ;
    • l'application peut aussi être livrée sous forme d'image de conteneur (Docker), que le greffon de Spring Boot sait produire sans fichier [Dockerfile] : [gradlew bootBuildImage]. L'image s'exécute ensuite sur n'importe quelle plateforme de conteneurs, chez soi ou chez un hébergeur ;
    • HTTPS est indispensable : les propriétés [server.ssl.*] de Spring Boot configurent le certificat du serveur Tomcat lorsque celui-ci est exposé directement.

    13.8. Conclusion

    Ce chapitre a présenté les services web REST/JSON, successeurs des services web SOAP, écrits en Kotlin avec Spring Boot et Spring MVC. Nous avons vu :

    • qu'un service web associe des URL et des méthodes HTTP à des fonctions Kotlin, grâce aux annotations [@RestController], [@GetMapping] et [@PostMapping], et que les paramètres de ces fonctions sont tirés de la route ([@PathVariable]), de la chaîne de requête ([@RequestParam]), du corps JSON ([@RequestBody]) ou du conteneur Spring (injection par le constructeur primaire) ;
    • que Spring comprend Kotlin : [runApplication], les paramètres nullables qui deviennent facultatifs, les constructeurs primaires et leurs valeurs par défaut ([@ConfigurationProperties]), à condition de lui donner la bibliothèque [kotlin-reflect] et d'appliquer le greffon [plugin.spring] ;
    • que les résultats sont envoyés en JSON par Jackson, à partir de classes de données, et les erreurs signalées par un code de statut et un document « Problem Details » ([ProblemDetail], [ResponseEntity], [@ExceptionHandler]) ;
    • qu'un client Kotlin utilise [java.net.http.HttpClient] et Jackson, et qu'un client écrit dans n'importe quel autre langage peut faire de même ;
    • que l'architecture en couches a tenu ses promesses : la version 9 du calcul de l'impôt réutilise sans modification les couches [dao] et [metier] de la version 5 côté serveur, et sa couche [ui] côté client ; il a suffi d'écrire le service web (une centaine de lignes) et une nouvelle implémentation de l'interface [IImpotMetier] (une cinquantaine de lignes).
