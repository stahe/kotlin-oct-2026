    10. L'accès aux bases de données avec JDBC

    10.1. Le pilote JDBC

    Reprenons l'architecture en couches utilisée à diverses reprises depuis le chapitre 6. Jusqu'à présent, la couche [dao] de l'application [Impots] a exploité trois types de sources de données :

    • des données placées « en dur » dans le code ([HardwiredImpot]) ;
    • des données provenant d'un fichier texte ([FileImpot]) ;
    • des données provenant d'un fichier JSON ([JsonImpot]).

    Nous étudions dans ce chapitre le cas où les données proviennent d'une base de données. L'architecture devient la suivante :

    Dans le schéma ci-dessus, la couche [dao] [1] dialogue avec le SGBD (Système de Gestion de Bases de Données) [3], qui gère la base de données [4], au travers d'une bibliothèque de classes propre au SGBD utilisé [2]. Cette bibliothèque implémente une API standard de la plateforme Java, JDBC (« Java DataBase Connectivity »), présente dans le JDK depuis sa version 1.1, en 1997. On l'appelle un pilote JDBC (« JDBC driver »). Tous les SGBD courants disposent d'un pilote JDBC, distribué sous la forme d'une archive [.jar].

    Kotlin n'a pas sa propre API d'accès aux bases de données : un programme Kotlin exécuté sur la JVM utilise JDBC directement, comme il utilise les fichiers NIO ou les threads du JDK. C'est l'un des grands atouts du langage : tous les pilotes JDBC écrits pour Java, et toutes les bibliothèques construites au-dessus d'eux, sont utilisables sans adaptation. Ce que Kotlin apporte, nous le verrons tout au long du chapitre, c'est une écriture plus concise et plus sûre du code JDBC : fonction [use] pour fermer les ressources, fonctions d'extension pour lire les résultats, classes de données pour représenter les lignes, absence d'exceptions contrôlées.

    JDBC est d'abord un ensemble d'interfaces, définies dans les paquetages [java.sql] et [javax.sql] du module [java.sql] du JDK : [Connection], [Statement], [PreparedStatement], [ResultSet], [DataSource]… Un pilote JDBC fournit des classes qui implémentent ces interfaces. Le code de l'application, lui, ne manipule que les interfaces : il ne contient pas, en général, le nom des classes du pilote. C'est une différence avec d'autres plateformes, où le code utilise souvent directement les classes propres à chaque SGBD ([MySqlConnection], [SqlConnection]… en C#) : sur la JVM, l'abstraction est la règle depuis l'origine, et changer de SGBD revient d'abord à changer de pilote et d'adresse de la base, comme nous le verrons. Il reste que chaque SGBD a son dialecte SQL : cette indépendance a des limites, que nous verrons aussi.

    Nous utilisons un seul SGBD, MySQL 8, que l'annexe « Le SGBD MySQL avec Laragon » installe sous Windows, et son pilote JDBC officiel, MySQL Connector/J, dans sa version 9.7.0. Les bases sont créées par des scripts SQL exécutés avec le client en ligne de commande [mysql] ; l'annexe montre aussi comment les créer avec le client graphique HeidiSQL livré avec Laragon.

    10.2. Les deux modes d'exploitation d'une source de données

    Une base de données peut être exploitée de deux manières différentes :

    • le mode connecté ;
    • le mode déconnecté.

    En mode connecté, l'application :

    • ouvre une connexion avec la source de données ;
    • travaille avec la source de données en lecture / écriture ;
    • ferme la connexion.

    En mode déconnecté, l'application :

    • ouvre une connexion avec la source de données ;
    • obtient une copie en mémoire de tout ou partie des données de la source ;
    • ferme la connexion ;
    • travaille avec la copie en mémoire des données, en lecture / écriture ;
    • lorsque le travail est fini, ouvre une connexion, envoie les données modifiées à la source de données pour qu'elle les prenne en compte, et ferme la connexion.

    Le mode connecté est celui de l'interface [ResultSet] de JDBC : les lignes du résultat d'une requête sont lues pendant que la connexion est ouverte. Le mode déconnecté est celui de l'interface [CachedRowSet] du paquetage [javax.sql.rowset] (Java 5) : une table en mémoire qui se remplit à partir d'une requête, se modifie hors connexion, puis renvoie ses modifications à la base. Ces « RowSet » sont toujours présents dans le JDK 25 mais ne sont plus guère utilisés dans les applications nouvelles : le travail sur une copie en mémoire des données, avec enregistrement ultérieur des modifications, est aujourd'hui confié à un ORM (« Object-Relational Mapper »), qui manipule des objets ordinaires plutôt que des lignes de tables. L'ORM le plus utilisé sur la JVM, Hibernate, est l'objet du chapitre 11 ; il s'utilise en Kotlin comme en Java. Nous étudions donc surtout le mode connecté, sur lequel repose d'ailleurs Hibernate, et nous ne montrerons le mode déconnecté que par un exemple, en fin de chapitre.

    10.3.2. Les quatre commandes de base du langage SQL

    SQL (« Structured Query Language ») est un langage, partiellement normalisé, d'interrogation et de mise à jour des bases de données. Tous les SGBD respectent la partie normalisée de SQL mais ajoutent au langage des extensions propriétaires qui exploitent leurs particularités. Nous en avons déjà rencontré deux exemples : la génération automatique des clés primaires et les types autorisés pour les colonnes d'une table dépendent souvent du SGBD.

    Les quatre commandes de base du langage SQL que nous présentons sont normalisées et acceptées par tous les SGBD :

    Commande
    Rôle
    [select col1, col2, … from table1, table2, … where condition order by expression]
    La requête qui permet d'obtenir les données contenues dans une base. Seuls les mots clés [select] et [from] sont obligatoires. Une jointure est faite avec toutes les tables qui suivent le mot clé [from] ; seules les colonnes qui suivent le mot clé [select] sont conservées ; seules les lignes vérifiant la condition du mot clé [where] sont conservées ; les lignes résultantes, ordonnées selon l'expression du mot clé [order by], forment le résultat de la requête. Ce résultat est une table.
    [insert into table(col1, col2, …) values (val1, val2, …)]
    Insère une ligne dans [table]. [(col1, col2, …)] précise les colonnes de la ligne à initialiser avec les valeurs [(val1, val2, …)].
    [update table set col1=val1, col2=val2, … where condition]
    Met à jour les lignes de [table] vérifiant [condition] (toutes les lignes s'il n'y a pas de [where]). Pour ces lignes, la colonne [coli] reçoit la valeur [vali].
    [delete from table where condition]
    Supprime toutes les lignes de [table] vérifiant [condition] (toutes les lignes s'il n'y a pas de [where]).

    10.3.3. Les interfaces de base de JDBC pour le mode connecté

    Revenons au schéma d'une application exploitant une base de données au travers d'un pilote JDBC :

    En mode connecté, l'application :

    • ouvre une connexion avec la source de données ;
    • travaille avec la source de données en lecture / écriture ;
    • ferme la connexion.

    Trois types d'objets sont principalement concernés par ces opérations :

    • la connexion ([Connection]), qui encapsule les propriétés et méthodes de la liaison avec la base ;
    • l'ordre SQL ([Statement], ou [PreparedStatement] pour un ordre paramétré), qui encapsule les propriétés et méthodes de l'ordre SQL exécuté ;
    • le résultat ([ResultSet]), qui encapsule les propriétés et méthodes du résultat d'un ordre SQL [select].

    Ce sont des interfaces du paquetage [java.sql]. Le pilote MySQL les implémente par des classes de ses propres paquetages ([com.mysql.cj.jdbc.ConnectionImpl], [ClientPreparedStatement], [ResultSetImpl]…), que l'application n'a pas à connaître : elle obtient ses objets par des méthodes qui rendent des interfaces. La connexion est obtenue de la classe [DriverManager] (ou d'une source de données [DataSource], que nous verrons plus loin), l'ordre SQL est créé par la connexion, le résultat est rendu par l'ordre SQL.

    Ces interfaces sont des interfaces Java. Kotlin les utilise avec ses règles habituelles d'accès au code Java : un couple d'accesseurs [getXxx] / [setXxx] s'utilise comme une propriété [xxx] ([resultat.metaData] plutôt que [resultat.getMetaData()], [connexion.autoCommit = false] plutôt que [connexion.setAutoCommit(false)]), et les valeurs rendues par une méthode Java ont un type de plate-forme (noté [String!] dans les messages du compilateur) : Kotlin ne sait pas si elles peuvent être [null] et laisse le développeur choisir de les traiter comme [String] ou comme [String?] (chapitre 3). Nous verrons que ce point compte pour les colonnes qui peuvent contenir la valeur SQL [NULL].

    10.3.3.1. L'interface Connection

    Elle sert à gérer la connexion avec la base de données. Une connexion est obtenue par la méthode statique [DriverManager.getConnection(url, utilisateur, motDePasse)], qui reçoit l'URL JDBC de la base, par exemple [jdbc:mysql://localhost:3306/dbarticles], et les identifiants de l'utilisateur. La connexion rendue est déjà ouverte. Les méthodes de l'interface [Connection] que nous utiliserons sont les suivantes :

    Méthode
    Rôle
    [createStatement]
    crée un ordre SQL [Statement] associé à cette connexion.
    [prepareStatement]
    [prepareStatement(sql)] crée un ordre SQL paramétré [PreparedStatement] associé à cette connexion.
    [prepareCall]
    [prepareCall("{call nom(?, ?)}")] crée un ordre [CallableStatement] qui exécute une procédure stockée dans la base.
    [autoCommit]
    [autoCommit = false] (la méthode Java [setAutoCommit]) démarre une transaction (voir plus loin).
    [commit], [rollback]
    valide, annule la transaction en cours.
    [metaData]
    (la méthode Java [getMetaData]) rend un objet [DatabaseMetaData] qui décrit le SGBD et le pilote.
    [isValid]
    [isValid(secondes)] vérifie que la connexion est toujours utilisable.
    [close]
    ferme la connexion, ainsi que les ordres SQL et les résultats qu'elle a créés.

    L'ouverture d'une connexion a la forme suivante (les schémas de code de ce paragraphe sont extraits du fichier [modeles/Modeles.kt] du projet, qui compile mais n'est pas exécuté) :

    10.3.3.3. L'interface ResultSet

    Elle encapsule les résultats d'un ordre SQL [select]. Un objet [ResultSet] représente une table avec des lignes et des colonnes, que l'on exploite séquentiellement : d'abord la première ligne, puis la deuxième, etc., sans retour en arrière possible (c'est le type par défaut [TYPE_FORWARD_ONLY] ; JDBC connaît aussi des résultats que l'on peut parcourir dans les deux sens, mais on les utilise rarement). Le [ResultSet] a un curseur placé initialement avant la première ligne : il faut appeler [next] pour lire la première ligne. Les méthodes de cette interface que nous utiliserons sont les suivantes :

    Méthode
    Rôle
    [next]
    passe à la ligne suivante de la table résultat. Rend [true] si la lecture a pu se faire, [false] s'il n'y a plus de ligne.

    [getInt(i)] rend la valeur entière de la colonne n° i de la ligne courante. Les colonnes sont numérotées à partir de 1, et non de 0. [getInt("nom")] rend la valeur de la colonne de nom [nom].     10.3.4. La gestion des erreurs

    La couche [dao] peut rencontrer de nombreuses erreurs lors de l'exploitation de la base de données : serveur arrêté, base inexistante, mot de passe incorrect, erreur de syntaxe SQL, violation d'une contrainte d'intégrité… Celles-ci sont remontées sous la forme d'exceptions [SQLException]. En Java, [SQLException] est une exception contrôlée : toutes les méthodes de JDBC la déclarent dans leur clause [throws], et le compilateur Java oblige le code qui les appelle à l'intercepter ou à la déclarer à son tour. Kotlin n'a pas d'exceptions contrôlées (chapitre 3) : le compilateur n'impose rien, et une fonction Kotlin qui appelle JDBC n'a rien à déclarer. C'est une liberté, et une responsabilité : rien ne signale au développeur qu'une ligne peut échouer, c'est à lui de décider où les erreurs sont traitées. Une couche [dao] doit gérer ces erreurs et, quoi qu'il arrive, libérer les ressources qu'elle a obtenues : la connexion, l'ordre SQL et le résultat doivent être fermés. Nous utiliserons souvent ces deux propriétés.

    L'intérêt de [use] n'est pas seulement l'économie de lignes : il évite au développeur de fermer lui-même la connexion. Or l'oubli de la fermeture d'une connexion peut passer inaperçu et « planter » l'application d'une façon qui paraîtra aléatoire, chaque fois que le SGBD (ou le pool de connexions, que nous verrons) atteindra le nombre maximal de connexions ouvertes qu'il peut supporter. Dans la suite du cours, toute ressource JDBC est ouverte par un use.

    La classe [SQLException] donne trois informations sur l'erreur, que Kotlin présente comme des propriétés :

    • [message] : le message d'erreur ;
    • [errorCode] : le code d'erreur propre au SGBD (le numéro d'erreur MySQL : 1049, 1062…) ;
    • [sqlState] : un code d'erreur de cinq caractères défini par la norme SQL (« SQLSTATE »), commun à tous les SGBD pour les erreurs les plus courantes : la classe [42] désigne une erreur de syntaxe ou d'accès, [23] une violation de contrainte d'intégrité, [08] une erreur de connexion…

    On notera la propriété [sqlState], issue de la méthode Java [getSQLState] : quand le nom commence par plusieurs majuscules, Kotlin les met en minuscules, sauf la dernière lorsqu'elle commence le mot suivant ([SQLState] devient [sqlState]).     10.3.7. Exécution d'une requête SELECT

    L'exécution d'ordres SQL comporte les étapes suivantes :

    • connexion à la base de données ;
    • émission des ordres SQL vers la base ;
    • traitement des résultats des ordres SQL ;
    • fermeture de la connexion.

    Les étapes 2 et 3 peuvent être répétées, la fermeture de la connexion n'ayant lieu qu'à la fin de l'exploitation de la base. Les connexions ouvertes sont des ressources limitées d'un SGBD : il faut les économiser, et l'on cherche toujours à limiter la durée de vie d'une connexion ouverte. Dans notre programme, la connexion est fermée après chaque ordre SQL, et une nouvelle connexion est ouverte pour l'ordre suivant.

    L'ouverture d'une connexion est pourtant coûteuse : il faut établir une connexion réseau avec le serveur, négocier éventuellement un chiffrement, s'authentifier. [DriverManager] ne fait rien pour diminuer ce coût : chaque appel à [getConnection] ouvre une nouvelle connexion réseau, et chaque [close] la ferme réellement. Pour un outil interactif comme celui-ci, ce n'est pas gênant. Une application qui exécute de nombreux ordres SQL, un serveur web par exemple, utilise au contraire un pool de connexions : lorsque l'application ferme une connexion, le pool ne la ferme pas réellement mais la remet dans un réservoir (le pool) ; lorsque l'application demande une nouvelle connexion, elle reçoit l'une des connexions du pool, déjà établie. L'intérêt de ce système est qu'il est transparent pour le développeur : le code qui ouvre et ferme ses connexions par un [use] n'a pas à être modifié. Nous verrons au paragraphe « Les sources de données et les pools de connexions » comment l'utiliser. Ouvrir une connexion au début de chaque opération et la fermer à la fin est donc la bonne pratique.

private fun executeSelect(parametres: ParametresConnexion, requete: String) {
    try {
        // la connexion, l'ordre SQL et le résultat sont fermés à la sortie de leur bloc [use]
        parametres.connecter().use { connexion ->
            connexion.createStatement().use { ordre ->
                ordre.executeQuery(requete).use { resultat ->
                    // affichage des résultats
                    afficherResultSet(resultat)
                }
            }
        }
    } catch (e: SQLException) {
        println("Erreur d'accès à la base de données (${e.message})")
    }
}

// affichage des lignes d'un résultat de select
private fun afficherResultSet(resultat: ResultSet) {
    // les noms des colonnes, donnés par les métadonnées du résultat
    val metadonnees = resultat.metaData
    val colonnes = 1..metadonnees.columnCount
    val entete = colonnes.joinToString(",") { metadonnees.getColumnLabel(it) }
    val tirets = "-".repeat(entete.length)
    println("\n$tirets\n$entete\n$tirets\n")
    // les lignes, l'une après l'autre
    while (resultat.next()) {
        println(colonnes.joinToString(" ") { "${resultat.getObject(it)}" })
    }
}

fun main(args: Array<String>) {
    // l'URL JDBC de la base
    val url = args.firstOrNull() ?: "jdbc:mysql://localhost:3306/dbarticles"

    // 1 - les pilotes JDBC trouvés dans le classpath
    println("Pilotes JDBC chargés :")
    for (pilote in DriverManager.drivers()) {
        println("  ${pilote.javaClass.name} ${pilote.majorVersion}.${pilote.minorVersion}")
    }

    // 2 - DriverManager choisit le pilote qui accepte l'URL
    try {
        DriverManager.getConnection(url, "root", "").use { connexion ->
            val metadonnees = connexion.metaData
            println("SGBD : ${metadonnees.databaseProductName} ${metadonnees.databaseProductVersion}")
            println("Pilote : ${metadonnees.driverName} ${metadonnees.driverVersion} " +
                    "(JDBC ${metadonnees.jdbcMajorVersion}.${metadonnees.jdbcMinorVersion})")
            afficherArticles(connexion)
        }
    } catch (ex: SQLException) {
        println("Erreur d'accès à la base de données (${ex.message})")
        return
    }

    // 3 - une source de données sans pool : chaque getConnection ouvre une connexion réseau
    val sansPool = MysqlDataSource().apply {
        setURL(url)
        user = "root"
        password = ""
    }
    mesurer("MysqlDataSource (sans pool)", sansPool)

    // 4 - une source de données avec un pool de connexions HikariCP
    val config = HikariConfig().apply {
        jdbcUrl = url
        username = "root"
        password = ""
        maximumPoolSize = 5
    }
    HikariDataSource(config).use { avecPool ->
        mesurer("HikariDataSource (pool)", avecPool)
    }

// une requête paramétrée exécutée au travers des seules interfaces de JDBC
private fun afficherArticles(connexion: Connection) {
    connexion.prepareStatement("select id, nom, prix from articles where prix > ?").use { ordre ->
        ordre.setInt(1, 200)
        ordre.executeQuery().use { resultat ->
            println("Objets créés : ${connexion.javaClass.simpleName}, ${ordre.javaClass.simpleName}, " +
                    resultat.javaClass.simpleName)
            while (resultat.next()) {
                println("  ${resultat.getInt(1)} ${resultat.getString(2)} ${resultat.getBigDecimal(3)}")
            }
        }
    }
}

    } catch (ex: SQLException) {
        println("Erreur d'accès à la base de données (${ex.message})")
    }

    10.4.2. Les sources de données et les pools de connexions

    [DriverManager] est la façon historique d'obtenir une connexion. Depuis JDBC 2.0, on lui préfère dans les applications une source de données, un objet qui implémente l'interface [javax.sql.DataSource]. Une source de données est configurée une fois pour toutes (URL, utilisateur, mot de passe, réglages du pilote) et fournit ensuite des connexions par sa méthode [getConnection()], sans paramètres (la propriété [connection] en Kotlin). Le code qui utilise la source de données ne connaît ni l'URL ni les identifiants : dans une application, c'est elle que l'on enregistre dans le conteneur d'injection de dépendances (chapitre 6), plutôt que les paramètres de connexion. Il existe deux grandes familles de sources de données :

    • celles fournies par les pilotes, comme [com.mysql.cj.jdbc.MysqlDataSource] pour MySQL. Comme [DriverManager], elles ouvrent une nouvelle connexion réseau à chaque appel de [getConnection] ;
    • celles qui gèrent un pool de connexions. La plus utilisée est HikariCP, le pool par défaut de Spring Boot. Son [getConnection] rend une connexion du pool, et le [close] de cette connexion la remet dans le pool au lieu de la fermer.

    La seconde partie du programme [Jdbc03] compare les deux (lignes 39-55 et fonction [mesurer]) :

    • lignes 40-43 : une source de données [MysqlDataSource]. La fonction de portée [apply] (chapitre 7) exécute le bloc avec l'objet créé comme receveur ([this]) puis rend cet objet : on peut ainsi configurer l'objet juste après sa création, sans répéter son nom. [user = "root"] appelle la méthode Java [setUser], et [password = ""] la méthode [setPassword]. Pour l'URL, il faut appeler [setURL(url)] : la classe [MysqlDataSource] a deux couples d'accesseurs, [getUrl] / [setUrl] et [getURL] / [setURL], qui deviendraient tous deux une propriété Kotlin [url] ; le compilateur refuse alors d'écrire [url = …] (« overload resolution ambiguity between candidates »).     • ligne 45 : la fonction [mesurer] reçoit la source de données sous le type de l'interface [DataSource] : elle conviendrait à n'importe quel pilote ;
    • lignes 48-52 : un objet [HikariConfig] réunit la configuration du pool : URL JDBC, identifiants et taille maximale du pool (5 connexions ; la valeur par défaut est 10). Il est lui aussi configuré par [apply], avec ses propriétés [jdbcUrl], [username], [password] et [maximumPoolSize].     • ligne 54 : la source de données [HikariDataSource] est créée à partir de cette configuration. Elle ouvre aussitôt ses premières connexions. Comme elle détient des connexions ouvertes, il faut la fermer à la fin du programme : [HikariDataSource] implémente [Closeable], et [use] s'en charge ;
    • lignes 74-82 : la fonction [mesurer] demande 100 fois une connexion à la source de données ([repeat(100) { … }]) et la ferme aussitôt. Le bloc modifie la variable [classe], déclarée par [var] hors du bloc : les lambdas de Kotlin peuvent modifier les variables qu'elles capturent (chapitre 7), ce que Java interdit.     10.4.3. Quel niveau d'abstraction choisir ?

    L'indépendance de JDBC vis-à-vis du SGBD semble idéale. Dans la pratique, JDBC n'arrive pas à cacher toutes les particularités d'un SGBD :

    • le SQL lui-même diffère d'un SGBD à l'autre dès qu'on sort des ordres de base : génération des clés primaires, limitation du nombre de lignes rendues ([limit 10] pour MySQL et PostgreSQL, [top 10] ou [offset … fetch] pour SQL Server), types des colonnes, fonctions de dates, etc. ;
    • les types rendus par [getObject] peuvent varier : nous verrons que le [count(*)] de MySQL rend un [Long] ;
    • les codes d'erreur ([errorCode]) sont propres à chaque SGBD, et les SQLSTATE ne sont pas toujours utilisés de la même façon ;
    • les URL et les paramètres de réglage sont propres à chaque pilote.

    Les paramètres des requêtes, en revanche, sont uniformes : JDBC impose la notation [?] (des paramètres positionnels, sans nom), que chaque pilote traduit dans la syntaxe de son SGBD.

    Pour s'affranchir de ces limites ou alléger l'écriture du code JDBC, on utilise aujourd'hui principalement :

    • un ORM, le plus souvent Hibernate, présenté au chapitre 11 : la couche [dao] manipule des objets et écrit ses requêtes en HQL, un langage de requêtes objet ; c'est Hibernate qui génère le SQL propre à chaque SGBD (son « dialecte ») ;
    • des bibliothèques qui gardent le SQL mais suppriment le code répétitif de JDBC : [JdbcTemplate] et [JdbcClient] de Spring (ce dernier depuis Spring Framework 6.1), qui transforment directement les lignes d'un [select] en objets et convertissent les [SQLException] en exceptions non contrôlées ; jOOQ, qui construit les requêtes SQL dans le code avec vérification par le compilateur, et propose des extensions pour Kotlin ; MyBatis, qui associe des requêtes SQL écrites dans des fichiers XML ou des annotations à des méthodes ;
    • côté Kotlin, Exposed, la bibliothèque d'accès aux bases de données de JetBrains, qui offre les deux styles : un langage de requêtes écrit en Kotlin ([Articles.selectAll().where { Articles.prix greater 200 }]) et une couche objet légère.

    Ces outils s'appuient tous sur JDBC : comprendre JDBC reste utile pour comprendre ce qu'ils font et diagnostiquer leurs problèmes. Et, nous allons le voir, quelques fonctions d'extension suffisent déjà à rendre le code JDBC écrit en Kotlin beaucoup moins répétitif.

    10.5. Les requêtes paramétrées

    10.5.1. Le principe

// des fonctions d'extension pour lire les lignes d'un ResultSet

// toutes les lignes (restantes) du résultat, chacune transformée par [transformation]
fun <T> ResultSet.toList(transformation: (ResultSet) -> T): List<T> {
    val liste = mutableListOf<T>()
    while (next()) {
        liste.add(transformation(this))
    }
    return liste
}

// les mêmes lignes, lues à la demande : la séquence doit être parcourue avant la fermeture du résultat
fun <T> ResultSet.asSequence(transformation: (ResultSet) -> T): Sequence<T> =
    generateSequence { if (next()) transformation(this) else null }

                    cles.next()
                    println("article [${article.nom}] inséré avec l'id ${cles.getInt(1)}")
                }
            }
        }
    }
}

    10.6. Les transactions

    10.6.1. Généralités

    Une transaction est une suite d'ordres SQL exécutée de façon « atomique » :

    • soit toutes les opérations réussissent ;
    • soit l'une d'elles échoue, et alors toutes celles qui l'ont précédée sont annulées.

    Au final, les opérations d'une transaction ont soit toutes été appliquées avec succès, soit aucune ne l'a été. L'exemple classique est le virement bancaire : le débit d'un compte et le crédit d'un autre doivent être faits tous les deux ou pas du tout. Lorsque l'application a elle-même la maîtrise de la transaction, elle la valide par un ordre [COMMIT] ou l'annule par un ordre [ROLLBACK].

    Dans nos exemples précédents, nous n'avons pas utilisé de transaction. Et pourtant il y en avait, car dans un SGBD un ordre SQL s'exécute toujours au sein d'une transaction. Si l'application ne démarre pas elle-même une transaction explicite, le SGBD utilise une transaction implicite. Il y a alors deux cas :

    • chaque ordre SQL fait l'objet d'une transaction, ouverte par le SGBD avant l'ordre et validée après. On dit qu'on est en mode autocommit. Tout se passe comme si l'application faisait une transaction pour chaque ordre SQL ;
    • le SGBD n'est pas en mode autocommit : il commence une transaction implicite au premier ordre SQL émis en dehors d'une transaction et laisse l'application la terminer. Tous les ordres SQL émis ensuite font partie de cette transaction implicite, qui peut se terminer sur différents événements (fermeture de la connexion, début d'une nouvelle transaction…), selon des règles propres au SGBD. C'est un mode à éviter.

    JDBC impose le premier cas : une connexion JDBC est en mode autocommit lorsqu'elle est ouverte, quel que soit le réglage du SGBD (MySQL, avec le moteur de stockage InnoDB utilisé par défaut, est d'ailleurs lui aussi en mode autocommit).

    Les ordres SQL des différents utilisateurs s'exécutent en même temps, dans des transactions qui travaillent en parallèle. Les opérations faites par une transaction peuvent affecter celles faites par une autre. On distingue quatre niveaux d'étanchéité (d'isolation) entre les transactions des différents utilisateurs :

    • Read Uncommitted ;
    • Read Committed ;
    • Repeatable Read ;
    • Serializable.

    Read Uncommitted

    Ce mode d'isolation est également appelé « Dirty Read ». Voici un exemple de ce qui peut se passer dans ce mode :

    • un utilisateur U1 commence une transaction sur une table T ;
    • un utilisateur U2 commence une transaction sur cette même table T ;
    • l'utilisateur U1 modifie des lignes de la table T mais ne les valide pas encore ;
    • l'utilisateur U2 « voit » ces modifications et prend des décisions à partir de ce qu'il voit ;
    • l'utilisateur U1 annule sa transaction par un [ROLLBACK].

    À l'étape 4, l'utilisateur U2 a pris une décision à partir de données qui se révèlent fausses ensuite.

    Read Committed

    Ce mode d'isolation évite l'écueil précédent : à l'étape 4, l'utilisateur U2 ne « voit » pas les modifications apportées par l'utilisateur U1 à la table T. Il ne les verra qu'après que U1 aura validé sa transaction par un [COMMIT]. Dans ce mode, on peut néanmoins rencontrer la situation suivante :

    • un utilisateur U1 commence une transaction sur une table T ;
    • un utilisateur U2 commence une transaction sur cette même table T ;
    • l'utilisateur U2 fait un [select] pour obtenir la moyenne d'une colonne C des lignes de T vérifiant une certaine condition ;
    • l'utilisateur U1 modifie ([update]) certaines valeurs de la colonne C de T et les valide ([commit]) ;
    • l'utilisateur U2 refait le même [select] qu'à l'étape 3. Il découvre que la moyenne de la colonne C a changé à cause des modifications faites par U1.

    L'utilisateur U2 ne voit plus que les modifications validées par U1, mais alors qu'il reste dans la même transaction, deux opérations identiques donnent des résultats différents. On appelle cette situation « Non-Repeatable Read ». Elle est ennuyeuse pour qui désire avoir une image stable de la table T.

    Repeatable Read

    Dans ce mode d'isolation, un utilisateur est assuré d'obtenir les mêmes résultats pour ses lectures de la base tant qu'il reste dans la même transaction. Il travaille sur une « photographie » des données sur laquelle ne sont pas répercutées les modifications apportées par les autres transactions, même validées. Il ne les verra que lorsqu'il aura lui-même terminé sa transaction.

    Ce mode d'isolation n'est pas encore parfait en théorie : une autre transaction peut ajouter ([insert]) des lignes vérifiant la condition de l'étape 3, qui changeraient le résultat d'une nouvelle lecture. On appelle ces lignes des lignes fantômes (« phantom read »). C'est le niveau d'isolation par défaut de MySQL (InnoDB), qui évite d'ailleurs aussi les lignes fantômes pour les lectures simples.

    Serializable

    Dans ce mode d'isolation, les transactions sont complètement étanches les unes des autres : le résultat de deux transactions menées simultanément est le même que si elles avaient été faites l'une après l'autre. Pour y parvenir, le SGBD verrouille les données lues et fait attendre (ou échouer) les transactions qui voudraient les modifier. Ce niveau diminue le parallélisme et donc les performances.

    Les quatre niveaux d'isolation ne sont pas disponibles dans tous les SGBD. Le niveau par défaut est en général Read Committed (SQL Server, PostgreSQL, Oracle) ou Repeatable Read (MySQL). Le niveau désiré peut être indiqué explicitement par l'application.

    Rôle
    [autoCommit]
    [autoCommit = false] ([setAutoCommit(false)] en Java) quitte le mode autocommit : les ordres SQL qui suivent font partie d'une transaction, qui commence avec le premier d'entre eux et se termine par [commit] ou [rollback]. Une nouvelle transaction commence alors avec l'ordre suivant. [autoCommit = true] revient au mode autocommit, en validant la transaction en cours.
    [commit()]
    valide la transaction : les résultats des ordres SQL émis dans la transaction deviennent définitifs et visibles des autres transactions.
    [rollback()]
    annule la transaction : les résultats des ordres SQL émis dans la transaction sont défaits.
    [setSavepoint()]
    pose un point de sauvegarde (« savepoint », un objet [Savepoint]) dans la transaction en cours. Ce n'est pas un accesseur (il n'a pas de [getSavepoint] associé) : Kotlin l'appelle comme une fonction.
    [rollback(Savepoint)]
    annule les ordres SQL exécutés depuis le point de sauvegarde, sans annuler ceux qui le précèdent : la transaction continue.
    [transactionIsolation]
    le niveau d'isolation des transactions de la connexion ([setTransactionIsolation] en Java). Il doit être fixé avant le début d'une transaction.

    Le niveau d'isolation est l'une des constantes de l'interface [Connection] :

    Valeur
    Signification
    [TRANSACTION_READ_UNCOMMITTED]
    la transaction peut lire des données écrites par une autre transaction que celle-ci n'a pas encore validées. À éviter.
    [TRANSACTION_READ_COMMITTED]
    la transaction ne peut pas lire des données écrites par une autre transaction que celle-ci n'a pas encore validées. Les données lues deux fois de suite dans la transaction peuvent cependant changer, car une autre transaction a pu les modifier entre-temps ; une autre transaction a aussi pu ajouter des lignes (lignes fantômes).
    [TRANSACTION_REPEATABLE_READ]
    les données lues par la transaction ne changent pas tant qu'elle n'est pas terminée. Cela n'évite pas, en théorie, l'ajout de lignes par une autre transaction.
    [TRANSACTION_SERIALIZABLE]
    tout se passe comme si la transaction était seule. Diminue les performances, car les transactions ne travaillent plus en parallèle.

    Ce sont des constantes [static] d'une interface Java : Kotlin les désigne par le nom de l'interface, [Connection.TRANSACTION_READ_COMMITTED], comme les membres d'un [companion object].

    Une connexion qui a quitté le mode autocommit doit être fermée après la validation ou l'annulation de sa transaction. Si elle est fermée avec une transaction en cours, le résultat dépend du pilote (MySQL Connector/J l'annule) : il faut toujours terminer explicitement une transaction.

import commun.Article
import commun.transaction
import java.math.BigDecimal
import java.sql.Connection
import java.sql.DriverManager
import java.sql.PreparedStatement
import java.sql.SQLException

// les transactions

private const val URL = "jdbc:mysql://localhost:3306/dbarticles"
private const val UTILISATEUR = "root"
private const val MOT_DE_PASSE = ""

fun main() {
    println("URL JDBC de la base : [$URL]")

    // deux articles de même nom : la contrainte d'unicité UNQ_NOM refusera le second
    val articles = listOf(
        Article(0, "article", BigDecimal("100"), 10, 1),
        Article(0, "article", BigDecimal("200"), 20, 2),
    )

    try {
        // 1 - insertion sans transaction explicite
        println("\nInsertion sans transaction...")
        executeUpdate("delete from articles")
        try {
            insertArticlesOutOfTransaction(articles)
        } catch (ex: SQLException) {
            println("Erreur d'accès à la base de données (${ex.message})")
        }
        afficherArticles()

        // 2 - la même chose dans une transaction
        println("\nInsertion dans une transaction...")
        executeUpdate("delete from articles")
        insertArticlesInTransaction(articles)
        afficherArticles()

        // 3 - une transaction avec un point de sauvegarde
        println("\nInsertion dans une transaction avec un point de sauvegarde...")
        executeUpdate("delete from articles")
        insertArticlesWithSavepoint(articles)
        afficherArticles()

        // 4 - une transaction gérée par la fonction d'ordre supérieur [transaction]
        println("\nInsertion dans une transaction gérée par la fonction [transaction]...")
        executeUpdate("delete from articles")
        try {
            insertArticlesWithFunction(articles)
        } catch (ex: SQLException) {
            println("transaction invalidée (${ex.message})")
        }
        insertArticlesWithFunction(articles.take(1))
        afficherArticles()
    } catch (ex: SQLException) {
        println("Erreur d'accès à la base de données (${ex.message})")
    }
}

// insertion d'une liste d'articles sans transaction explicite (mode autocommit)
private fun insertArticlesOutOfTransaction(articles: List<Article>) {
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        creerOrdreInsert(connexion).use { ordre ->
            articles.forEach { insererArticle(ordre, it) }
        }
    }
}

// insertion d'une liste d'articles dans une transaction
private fun insertArticlesInTransaction(articles: List<Article>) {
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        // début de la transaction : on quitte le mode autocommit
        connexion.transactionIsolation = Connection.TRANSACTION_READ_COMMITTED
        connexion.autoCommit = false
        try {
            creerOrdreInsert(connexion).use { ordre ->
                articles.forEach { insererArticle(ordre, it) }
            }
            // tout s'est bien passé : on valide la transaction
            connexion.commit()
            println("transaction validée...")
        } catch (ex: SQLException) {
            // une insertion a échoué : on défait la transaction
            connexion.rollback()
            println("transaction invalidée (${ex.message})")
        }
    }
}

// insertion dans une transaction : l'échec d'une insertion n'annule que ce qui suit
// le dernier point de sauvegarde
private fun insertArticlesWithSavepoint(articles: List<Article>) {
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        connexion.autoCommit = false
        try {
            creerOrdreInsert(connexion).use { ordre ->
                for (article in articles) {
                    // un point de sauvegarde avant chaque insertion
                    val avantInsertion = connexion.setSavepoint()
                    try {
                        insererArticle(ordre, article)
                    } catch (ex: SQLException) {
                        // seule l'insertion ratée est défaite
                        connexion.rollback(avantInsertion)
                        println("insertion de [${article.nom}, ${article.prix}] annulée (${ex.message})")
                    }
                }
            }
            connexion.commit()
            println("transaction validée...")
        } catch (ex: SQLException) {
            connexion.rollback()
            println("transaction invalidée (${ex.message})")
        }
    }
}

// insertion dans une transaction gérée par la fonction [transaction] : les exceptions sont propagées
private fun insertArticlesWithFunction(articles: List<Article>) {
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        val nbArticles = connexion.transaction(Connection.TRANSACTION_READ_COMMITTED) {
            // dans le bloc, [this] est la connexion
            creerOrdreInsert(this).use { ordre ->
                articles.forEach { insererArticle(ordre, it) }
            }
            articles.size
        }
        println("transaction validée : $nbArticles article(s) inséré(s)")
    }
}

// l'ordre paramétré d'insertion d'un article
private fun creerOrdreInsert(connexion: Connection): PreparedStatement = connexion.prepareStatement(
    "insert into articles(nom, prix, stockactuel, stockminimum) values(?, ?, ?, ?)"
)

// insertion d'un article avec l'ordre paramétré
private fun insererArticle(ordre: PreparedStatement, article: Article) {
    with(article) {
        ordre.setString(1, nom)
        ordre.setBigDecimal(2, prix)
        ordre.setInt(3, stockActuel)
        ordre.setInt(4, stockMinimum)
        ordre.executeUpdate()
        println("article [$nom, $prix] inséré")
    }
}

// exécution d'un ordre de mise à jour
private fun executeUpdate(requete: String) {
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        connexion.createStatement().use { ordre ->
            println("Il y a eu ${ordre.executeUpdate(requete)} ligne(s) modifiée(s)")
        }
    }
}

// affichage du contenu de la table
private fun afficherArticles() {
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        connexion.createStatement().use { ordre ->
            val requete = "select id, nom, prix, stockactuel, stockminimum from articles"
            ordre.executeQuery(requete).use { resultat ->
                println("Contenu de la table [articles] :")
                while (resultat.next()) {
                    // dans le bloc de with, [this] est le résultat : getInt(1) est resultat.getInt(1)
                    val ligne = with(resultat) {
                        "${getInt(1)} ${getString(2)} ${getBigDecimal(3)} ${getInt(4)} ${getInt(5)}"
                    }
                    println("  $ligne")
                }
            }
        }
    }
}

    package commun

import java.sql.Connection
import java.sql.SQLException

// exécute [bloc] dans une transaction de la connexion :
// - validée (commit) si le bloc se termine normalement ;
// - annulée (rollback) s'il lance une exception, qui est ensuite relancée ;
// le mode autocommit de la connexion est rétabli à la fin
// [crossinline] : le bloc ne peut pas contenir de return qui quitterait la fonction appelante
inline fun <T> Connection.transaction(isolation: Int? = null, crossinline bloc: Connection.() -> T): T {
    // le niveau d'isolation éventuel est fixé avant le début de la transaction
    isolation?.let { transactionIsolation = it }
    val autoCommitInitial = autoCommit
    autoCommit = false
    try {
        val resultat = bloc()
        commit()
        return resultat
    } catch (e: Throwable) {
        try {
            rollback()
        } catch (ex: SQLException) {
            // l'échec du rollback ne doit pas masquer l'exception d'origine
            e.addSuppressed(ex)
        }
        throw e
    } finally {
        autoCommit = autoCommitInitial
    }
}
    • ligne 11 : la fonction [transaction] est une fonction d'extension de l'interface [Connection] : on l'appelle comme une méthode de la connexion, [connexion.transaction { … }]. Elle a deux paramètres :
      • [isolation], le niveau d'isolation, de type [Int?] et de valeur par défaut [null] (le niveau de la connexion est alors inchangé) ;
      • [bloc], le travail à faire dans la transaction. Son type, [Connection.() -> T], est celui d'une lambda avec receveur : dans le bloc, [this] est la connexion, et l'on peut écrire [prepareStatement(…)] au lieu de [connexion.prepareStatement(…)]. C'est le mécanisme qu'utilisent [with], [apply] ou [buildList] de la bibliothèque standard. Le bloc rend une valeur de type [T], que [transaction] rend à son tour. Le bloc étant le dernier paramètre, il s'écrit après les parenthèses de l'appel, ou sans parenthèses du tout s'il est le seul argument ;
    • [inline] : le code de la fonction et celui du bloc sont recopiés à l'endroit de l'appel (chapitre 7) : aucun objet lambda n'est créé à chaque transaction. Mais une lambda passée à une fonction [inline] peut contenir un [return] qui quitte la fonction appelante (un retour « non local », comme dans le corps d'une boucle). Ici, ce serait un piège : un [return] au milieu du bloc sortirait du [try] sans passer ni par [commit] ni par [rollback], et la transaction resterait en suspens. Le modificateur [crossinline] du paramètre [bloc] l'interdit. Le compilateur refuse alors un bloc comme [connexion.transaction { if (nom.isEmpty()) return … }] :

    • lignes 14-15 : on mémorise le mode de la connexion, puis on quitte le mode autocommit ;

// le résultat est null si le select ne rend aucune ligne ou si la valeur est SQL NULL
private fun valeurUnique(requete: String): Any? =
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        connexion.createStatement().use { ordre ->
            ordre.executeQuery(requete).use { resultat ->
                if (resultat.next()) resultat.getObject(1) else null
            }
        }
    }

// la même chose, la valeur étant convertie par le pilote dans le type T demandé
// [reified] : le type T est connu à l'exécution, T::class.java est la classe Java de T

    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        connexion.createStatement().use { ordre ->
            ordre.executeQuery(requete).use { resultat ->
                if (resultat.next()) resultat.getObject(1, T::class.java) else null
            }
        }
    }

    10.8. JDBC est bloquant : threads virtuels et coroutines

    10.8.1. Les threads virtuels

    Le chapitre 9 a montré que les opérations d'entrées / sorties ne doivent pas immobiliser un thread de l'application dans les applications qui servent de nombreux utilisateurs (serveurs, services web) : pendant qu'un ordre SQL s'exécute sur le serveur, le thread qui l'a émis attend. Or JDBC est une API bloquante : [getConnection], [executeQuery], [next], [commit]… ne rendent la main que lorsque le SGBD a répondu. Il n'existe pas de version asynchrone de JDBC : un projet d'API asynchrone (ADBA) a été abandonné en 2019, et l'API réactive R2DBC, qui existe en dehors du JDK, n'a pas remplacé JDBC. Il n'existe pas davantage de version « suspendue » de JDBC pour les coroutines : une fonction JDBC appelée dans une coroutine bloque le thread qui exécute la coroutine.

    Depuis Java 21, la réponse de la plateforme Java est le thread virtuel (chapitre 8) : un thread léger, géré par la JVM, dont on peut créer des milliers. Lorsqu'un thread virtuel attend une réponse du réseau, la JVM le met de côté et libère le thread du système qui l'exécutait, qui peut alors exécuter un autre thread virtuel. Le code reste séquentiel et bloquant, simple à écrire et à lire, mais l'attente ne coûte plus rien. Les pilotes JDBC récents, dont Connector/J 9, sont écrits pour fonctionner avec les threads virtuels, et depuis Java 24 (JEP 491) un thread virtuel qui attend dans un bloc [synchronized] ne monopolise plus le thread du système. Kotlin, qui s'exécute sur la JVM, en profite sans rien faire de particulier.

    Il reste une limite : le nombre de connexions. Mille threads virtuels qui interrogent la base n'ont pas mille connexions : ils se partagent celles du pool, et attendent qu'une connexion se libère. Le programme [Jdbc08.kt] le montre, avec un pool HikariCP de quatre connexions :

fun main() {
    // la source de données : un pool d'au plus 4 connexions vers la base [dbarticles]
    val config = HikariConfig().apply {
        jdbcUrl = "jdbc:mysql://localhost:3306/dbarticles"
        username = "root"
        password = ""
        maximumPoolSize = 4
    }

    try {
        HikariDataSource(config).use { dataSource ->
            // 1 - un ordre de mise à jour, dans une transaction
            dataSource.connection.use { connexion ->
                val nbLignes = connexion.transaction {
                    prepareStatement("update articles set prix = prix * 1.1 where prix < ?").use { ordre ->
                        ordre.setInt(1, 200)
                        ordre.executeUpdate()
                    }
                }
                println("$nbLignes prix augmenté(s) de 10 %")
            }

            // 2 - six requêtes concurrentes, chacune dans son thread virtuel
            val duree = measureTime {
                val taches = Executors.newVirtualThreadPerTaskExecutor().use { executor ->
                    (1..6).map { id -> executor.submit(Callable { getArticleLentement(dataSource, id) }) }
                } // la fermeture de l'executor attend la fin des six tâches
                taches.forEach { println(it.get()) }
            }
            println("6 requêtes d'une seconde exécutées en %.1f s avec %d connexions"
                .format(duree.toDouble(DurationUnit.SECONDS), config.maximumPoolSize))

            // 3 - une valeur unique
            dataSource.connection.use { connexion ->
                connexion.createStatement().use { ordre ->
                    ordre.executeQuery("select sum(prix * stockactuel) from articles").use { resultat ->
                        resultat.next()
                        println("Valeur du stock : ${resultat.getBigDecimal(1)} euros")
                    }
                }
            }

            // 4 - une requête bloquée par une autre transaction, abandonnée au bout d'une seconde
            // la transaction [bloquante] modifie l'article n° 1 et ne se termine pas :
            // la ligne reste verrouillée
            dataSource.connection.use { bloquante ->
                bloquante.autoCommit = false
                bloquante.createStatement().use { ordre ->
                    ordre.executeUpdate("update articles set stockactuel = stockactuel - 1 where id = 1")
                }
                // une autre connexion veut modifier la même ligne : elle doit attendre la fin de [bloquante]
                val chrono = TimeSource.Monotonic.markNow()
                try {
                    dataSource.connection.use { connexion ->
                        connexion.createStatement().use { ordre ->
                            ordre.queryTimeout = 1
                            ordre.executeUpdate("update articles set prix = prix * 2 where id = 1")
                        }
                    }
                } catch (ex: SQLTimeoutException) {
                    val secondes = chrono.elapsedNow().inWholeSeconds
                    println("${ex::class.simpleName} au bout de $secondes s : ${ex.message}")
                }
                // la transaction [bloquante] n'a pas été validée : on la défait
                bloquante.rollback()
            }
        }
    } catch (ex: SQLException) {
        println("Erreur d'accès à la base de données (${ex.message})")
    } catch (ex: ExecutionException) {
        println("Erreur d'accès à la base de données (${ex.message})")
    }
}

fun main() = runBlocking {
    // la source de données : un pool d'au plus 4 connexions vers la base [dbarticles]
    val config = HikariConfig().apply {
        jdbcUrl = "jdbc:mysql://localhost:3306/dbarticles"
        username = "root"
        password = ""
        maximumPoolSize = 4
    }
    HikariDataSource(config).use { dataSource ->
        // 1 - six requêtes concurrentes exécutées par les threads du dispatcher IO
        lireSixArticles(dataSource, Dispatchers.IO, "Dispatchers.IO")
        // 2 - pas plus de requêtes simultanées que de connexions : une vue limitée du dispatcher IO
        lireSixArticles(dataSource, Dispatchers.IO.limitedParallelism(4), "IO.limitedParallelism(4)")
        // 3 - un dispatcher qui exécute chaque coroutine dans un thread virtuel
        Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher().use { virtuel ->
            lireSixArticles(dataSource, virtuel, "threads virtuels")
        }
        // 4 - withTimeout n'interrompt pas un appel JDBC bloquant
        val duree = measureTime {
            try {
                withTimeout(300) { getArticleLentement(dataSource, 1, Dispatchers.IO) }
            } catch (ex: TimeoutCancellationException) {
                println("withTimeout(300) : ${ex.message}")
            }
        }
        println("... mais l'exception n'est arrivée qu'après ${duree.toString(DurationUnit.SECONDS, 1)}")
    }
}

// lecture concurrente des articles 1 à 6, chacun par une requête d'une seconde
private suspend fun lireSixArticles(
    dataSource: DataSource,
    dispatcher: CoroutineDispatcher,
    nom: String,
) {
    val duree = measureTime {
        val articles = coroutineScope {
            (1..6).map { id -> async { getArticleLentement(dataSource, id, dispatcher) } }.awaitAll()
        }
        println(articles.joinToString { it.nom })
    }
    println("  $nom : 6 requêtes d'une seconde exécutées en ${duree.toString(DurationUnit.SECONDS, 1)}")
}

// un article lu par une requête qui dure une seconde : une fonction de suspension
// qui exécute le code JDBC bloquant sur un thread du dispatcher reçu
private suspend fun getArticleLentement(
    dataSource: DataSource,
    id: Int,
    dispatcher: CoroutineDispatcher,
): Article =
    withContext(dispatcher) {
        dataSource.connection.use { connexion ->
            connexion.prepareStatement(
                "select id, nom, prix, stockactuel, stockminimum, sleep(1) from articles where id = ?"
            ).use { ordre ->
                ordre.setInt(1, id)
                ordre.executeQuery().use { resultat ->
                    resultat.next()
                    resultat.toArticle()
                }
            }
        }
    }

    10.9. L'exécution par lots

    Chaque exécution d'un ordre SQL est un aller-retour entre l'application et le serveur. Lorsqu'on doit exécuter plusieurs ordres SQL, on peut les envoyer au SGBD en un seul échange, sous la forme d'un lot (« batch »). JDBC le permet depuis sa version 2.0 :

    • pour un [Statement], [addBatch(sql)] ajoute un ordre SQL au lot ;
    • pour un [PreparedStatement], [addBatch()] ajoute au lot les valeurs actuelles des paramètres : le lot contient le même ordre SQL exécuté avec différentes valeurs ;
    • [executeBatch] exécute le lot et rend un tableau d'entiers ([IntArray] en Kotlin) : le nombre de lignes modifiées par chaque ordre du lot. Si un ordre échoue, elle lance une [BatchUpdateException] dont la méthode [getUpdateCounts] (la propriété [updateCounts] en Kotlin) donne les résultats des ordres exécutés.

import commun.transaction
import java.math.BigDecimal
import java.sql.DriverManager
import java.sql.SQLException
import kotlin.time.measureTimedValue

// l'exécution par lots : plusieurs ordres SQL envoyés au SGBD en un seul échange

private const val URL = "jdbc:mysql://localhost:3306/dbarticles"
private const val UTILISATEUR = "root"
private const val MOT_DE_PASSE = ""

fun main() {
    try {
        DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
            println("Le pilote sait exécuter des lots : ${connexion.metaData.supportsBatchUpdates()}")

            // 1 - un lot de trois ordres de mise à jour différents
            connexion.createStatement().use { ordre ->
                ordre.addBatch(
                    "insert into articles(nom, prix, stockactuel, stockminimum) values('canoë', 800, 5, 1)"
                )
                ordre.addBatch(
                    "update articles set stockactuel = stockactuel + 10 where stockactuel < stockminimum"
                )
                ordre.addBatch("delete from articles where nom = 'pompe'")
                val nbLignes: IntArray = ordre.executeBatch()
                println("Lignes modifiées par chaque ordre : ${nbLignes.contentToString()}, "
                    + "total : ${nbLignes.sum()}")
            }
        }
        // 2 - 1000 insertions par un lot du même ordre paramétré, sans puis avec réécriture du lot
        insererLot(URL, 1000)
        insererLot("$URL?rewriteBatchedStatements=true", 1000)
    } catch (ex: SQLException) {
        println("Erreur d'accès à la base de données (${ex.message})")
    }

    // 3 - deux select envoyés en un seul échange : un ordre, deux résultats successifs
    try {
        val url = "$URL?allowMultiQueries=true"
        DriverManager.getConnection(url, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
            connexion.createStatement().use { ordre ->
                ordre.execute(
                    """
                    select nom, stockactuel from articles where stockactuel < stockminimum + 5;
                    select count(*), sum(prix * stockactuel) from articles
                    """.trimIndent()
                )
                println("Articles à surveiller :")
                ordre.resultSet.use { resultat ->
                    while (resultat.next()) {
                        println("  ${resultat.getString(1)} : ${resultat.getInt(2)}")
                    }
                }
                // passage au résultat suivant
                ordre.getMoreResults()
                ordre.resultSet.use { resultat ->
                    resultat.next()
                    val (nombre, valeur) = resultat.getLong(1) to resultat.getBigDecimal(2)
                    println("$nombre articles, valeur du stock : $valeur euros")
                }
            }
        }
    } catch (ex: SQLException) {
        println("Erreur d'accès à la base de données (${ex.message})")
    }
}

// insertion de n articles par un lot, dans une transaction, puis suppression de ces articles
private fun insererLot(url: String, n: Int) {
    DriverManager.getConnection(url, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        // measureTimedValue rend la valeur du bloc et sa durée d'exécution
        val (nbLignes, duree) = measureTimedValue {
            connexion.transaction {
                prepareStatement(
                    "insert into articles(nom, prix, stockactuel, stockminimum) values(?, ?, ?, ?)"
                ).use { ordre ->
                    for (i in 1..n) {
                        ordre.setString(1, "lot-$i")
                        ordre.setBigDecimal(2, BigDecimal.TEN)
                        ordre.setInt(3, i)
                        ordre.setInt(4, 0)
                        // les valeurs des paramètres sont ajoutées au lot
                        ordre.addBatch()
                    }
                    ordre.executeBatch()
                }
            }
        }
        val base = url.substringAfterLast('/')
        val ms = duree.inWholeMilliseconds
        println("${nbLignes.size} insertions ($base) en $ms ms : ${nbLignes.take(3)}...")
        // on remet la table dans son état précédent
        connexion.createStatement().use { ordre ->
            ordre.executeUpdate("delete from articles where nom like 'lot-%'")
        }
    }
}

import java.math.BigDecimal
import java.sql.DriverManager
import java.sql.SQLException
import javax.sql.rowset.RowSetProvider

// le mode déconnecté : une copie en mémoire des lignes, modifiée hors connexion puis renvoyée à la base

private const val URL = "jdbc:mysql://localhost:3306/dbarticles"
private const val UTILISATEUR = "root"
private const val MOT_DE_PASSE = ""

fun main() {
    try {
        // la fabrique des RowSet de la plateforme Java
        val fabrique = RowSetProvider.newFactory()
        fabrique.createCachedRowSet().use { articles ->
            // les paramètres de connexion et la requête
            articles.url = URL
            articles.username = UTILISATEUR
            articles.password = MOT_DE_PASSE
            articles.command = "select id, nom, prix, stockactuel, stockminimum from articles"
            // la table à mettre à jour et sa clé primaire (colonne n° 1)
            articles.tableName = "articles"
            articles.keyColumns = intArrayOf(1)
            // connexion, copie des lignes en mémoire, déconnexion
            articles.execute()
            println("${articles.size()} lignes copiées en mémoire")

            // travail hors connexion : réapprovisionnement des articles en rupture de stock
            while (articles.next()) {
                val stockActuel = articles.getInt("stockactuel")
                val stockMinimum = articles.getInt("stockminimum")
                if (stockActuel < stockMinimum) {
                    articles.updateInt("stockactuel", stockMinimum + 10)
                    articles.updateRow()
                    val nom = articles.getString("nom")
                    println("[$nom] : stock $stockActuel -> ${articles.getInt("stockactuel")}")
                }
            }
            // ajout d'une ligne : l'id 0 demande à MySQL d'en générer un
            with(articles) {
                moveToInsertRow()
                updateInt("id", 0)
                updateString("nom", "canoë")
                updateBigDecimal("prix", BigDecimal("800"))
                updateInt("stockactuel", 5)
                updateInt("stockminimum", 1)
                insertRow()
                moveToCurrentRow()
            }
            // suppression de la 2e ligne
            articles.absolute(2)
            println("suppression de [${articles.getString("nom")}]")
            articles.deleteRow()

            // la base n'a pas encore été modifiée
            afficherArticles("Base avant acceptChanges :")
            // connexion, envoi des modifications dans une transaction, déconnexion
            DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
                connexion.autoCommit = false
                articles.acceptChanges(connexion)
            }
        }
        afficherArticles("Base après acceptChanges :")
    } catch (ex: SQLException) {
        println("Erreur d'accès à la base de données (${ex.message})")
    }
}

// affichage du contenu de la table, lu en mode connecté
private fun afficherArticles(titre: String) {
    DriverManager.getConnection(URL, UTILISATEUR, MOT_DE_PASSE).use { connexion ->
        connexion.createStatement().use { ordre ->
            val requete = "select id, nom, prix, stockactuel, stockminimum from articles"
            ordre.executeQuery(requete).use { resultat ->
                println(titre)
                while (resultat.next()) {
                    val ligne = with(resultat) {
                        "${getInt(1)} ${getString(2)} ${getBigDecimal(3)} ${getInt(4)} ${getInt(5)}"
                    }
                    println("  $ligne")
                }
            }
        }
    }
}

    Le [CachedRowSet] a l'avantage d'être une API standard du JDK, mais on voit ses limites : on manipule des lignes et des noms ou numéros de colonnes, et non des objets métier ; les modifications sont faites par une implémentation dont on maîtrise mal le SQL. C'est pourquoi il est peu utilisé aujourd'hui : le travail sur des objets en mémoire avec enregistrement ultérieur des modifications est le domaine des ORM comme Hibernate (chapitre 11).

// une couche [dao] qui lit les tranches d'impôt dans une base MySQL
// la requête a une valeur par défaut : un seul constructeur suffit
class MySqlImpot(
    url: String,
    utilisateur: String,
    motDePasse: String,
    requete: String = REQUETE_PAR_DEFAUT,
) : IImpotDao {

    // tranches d'impôt, lues une fois pour toutes à la construction de l'objet
    override val tranchesImpot: List<TrancheImpot>

    init {
        val tranches: List<TrancheImpot> = try {
            DriverManager.getConnection(url, utilisateur, motDePasse).use { connexion ->
                connexion.createStatement().use { ordre ->
                    ordre.executeQuery(requete).use { resultat ->
                        // une tranche par ligne du résultat : limite, coeffR, coeffN
                        buildList {
                            while (resultat.next()) {
                                add(lireTranche(resultat))
                            }
                        }
                    }
                }
            }
        } catch (e: SQLException) {
            // erreur d'accès à la base : on l'encapsule dans une ImpotException
            throw ImpotException("Erreur d'accès à la base des tranches d'impôt", e, ACCES)
        }
        // une table vide est aussi une erreur
        if (tranches.isEmpty()) {
            throw ImpotException("La base ne contient aucune tranche d'impôt", code = DONNEES)
        }
        // buildList rend une liste en lecture seule
        tranchesImpot = tranches
    }

    companion object {
        // codes d'erreur propres à cette implémentation
        const val ACCES = 101
        const val DONNEES = 102

        // la requête par défaut : les tranches doivent être rendues dans l'ordre croissant des limites
        const val REQUETE_PAR_DEFAUT = "select limite, coeffr, coeffn from tranches order by id"

        // la tranche de la ligne courante : trois colonnes numériques, sans valeur NULL
        private fun lireTranche(resultat: ResultSet): TrancheImpot {
            // getBigDecimal rend null pour une valeur SQL NULL : le type est donc BigDecimal?
            val colonnes: List<BigDecimal?> = try {
                (1..3).map { resultat.getBigDecimal(it) }
            } catch (e: SQLException) {
                // une colonne absente ou non numérique
                throw ImpotException("Les tranches d'impôt de la base sont incorrectes", e, DONNEES)
            }
            val (limite, coeffR, coeffN) = colonnes
            if (limite == null || coeffR == null || coeffN == null) {
                throw ImpotException("Une tranche d'impôt de la base a une valeur NULL", code = DONNEES)
            }
            // ici, les trois valeurs sont de type BigDecimal (transtypage intelligent)
            return TrancheImpot(limite, coeffR, coeffN)
        }
    }

    La couche [dao] [MySqlImpot] n'utilise que les interfaces de JDBC : malgré son nom, elle n'est pas propre à MySQL (un nom comme [JdbcImpot] lui conviendrait mieux). Pour utiliser une base PostgreSQL (ou SQL Server, ou Oracle), il suffirait :

    • de créer la table des tranches dans une base PostgreSQL, par exemple une table [data] de colonnes [data1], [data2], [data3], pour souligner l'intérêt de placer la requête dans la configuration ;
    • d'ajouter au fichier [build.gradle.kts] du sous-projet [impots-ui-mysql] la dépendance du pilote JDBC de PostgreSQL, [runtimeOnly("org.postgresql:postgresql:…")] (ou [com.microsoft.sqlserver:mssql-jdbc], [com.oracle.database.jdbc:ojdbc11]) ;
    • d'écrire un fichier de configuration analogue à [impots.properties], comme le fichier [impots-postgresql.properties] du sous-projet :

Les couches [metier] et [ui], la classe [MySqlImpot] et le programme [Main.kt] n'ont pas à être modifiés : seuls changent la configuration et le pilote présent dans le classpath. Une couche [dao] plus riche (recherches, mises à jour) rencontrerait vite les particularités du SQL de chaque SGBD vues plus haut : c'est là qu'un ORM comme Hibernate prend le relais.

    10.12. Conclusion

    Ce chapitre a présenté l'accès aux bases de données avec JDBC, depuis Kotlin :

    • JDBC est un ensemble d'interfaces ([Connection], [Statement], [PreparedStatement], [ResultSet], [DataSource]…) des paquetages [java.sql] et [javax.sql], implémentées par un pilote propre à chaque SGBD (MySQL Connector/J pour MySQL), que [DriverManager] choisit d'après l'URL JDBC de la base. Kotlin n'a pas d'API propre : il utilise JDBC directement, avec ses accesseurs vus comme des propriétés ([connexion.autoCommit = false]) ;
    • une connexion est ouverte le plus tard possible et fermée le plus tôt possible, par la fonction [use] ; un pool de connexions comme HikariCP, au travers de l'interface [DataSource], rend cette pratique peu coûteuse ;
    • [executeQuery] exécute un [select] et rend un [ResultSet] qu'on parcourt ligne à ligne avec [next], en lisant les colonnes, numérotées à partir de 1, par les méthodes [getXxx] ; des fonctions d'extension ([toList], [asSequence], [toArticle]) transforment les lignes en objets Kotlin. [executeUpdate] exécute un [insert], [update] ou [delete] et rend le nombre de lignes modifiées ;
    • les erreurs sont des [SQLException], qui donnent un code d'erreur propre au SGBD et un code SQLSTATE normalisé. Elles sont contrôlées en Java, pas en Kotlin, qui n'oblige à rien : c'est au développeur de décider où les intercepter, typiquement dans la couche [dao] qui les encapsule dans ses propres exceptions ;
    • les valeurs extérieures sont toujours passées par les paramètres d'un [PreparedStatement], jamais insérées dans le texte de la requête, ni par concaténation ni par un gabarit de chaîne, ce qui protège de l'injection SQL ;
    • les transactions ([autoCommit = false], [commit], [rollback], points de sauvegarde) rendent atomique une suite d'ordres SQL ; une fonction d'ordre supérieur comme notre [connexion.transaction { … }] en cache la mécanique ;
    • JDBC est bloquant : les threads virtuels permettent de servir de nombreux utilisateurs avec un code JDBC ordinaire, dans la limite de la taille du pool ; les coroutines l'intègrent en enveloppant les appels dans [withContext(Dispatchers.IO)], de préférence avec un parallélisme limité à la taille du pool. Les lots ([addBatch], [executeBatch]) réduisent le nombre d'échanges avec le serveur ;
    • le mode déconnecté ([CachedRowSet]) existe, mais le travail sur des objets en mémoire est aujourd'hui le domaine des ORM.

    La version 6 de l'application [Impots] a montré que, grâce à l'architecture en couches, passer d'un fichier à une base de données ne demande que d'écrire une nouvelle couche [dao] et de modifier la configuration ; la construction composite de Gradle a permis de réutiliser la version 5 sans la copier ni l'installer. Le chapitre suivant écrira une septième version de cette couche avec Hibernate, qui génère lui-même les ordres SQL.

    Entre le JDBC « brut » de ce chapitre et un ORM complet comme Hibernate, l'écosystème Kotlin et Java offre des bibliothèques intermédiaires, qui gardent le contrôle du SQL en supprimant le code répétitif :

    • Exposed, la bibliothèque d'accès aux bases de données de JetBrains, écrite en Kotlin : les tables sont décrites par des objets Kotlin, et les requêtes s'écrivent dans un langage dédié (DSL) typé, [Articles.selectAll().where { Articles.prix less 200 }], dans des blocs [transaction { … }] ; elle propose aussi une couche d'objets (DAO) plus proche d'un ORM ;
    • jOOQ, qui génère à partir du schéma de la base des classes Java utilisables depuis Kotlin, et permet d'écrire des requêtes SQL vérifiées à la compilation ;
    • Spring JDBC, dont l'interface [JdbcClient] (Spring 6.1) exécute une requête paramétrée et transforme ses lignes en objets en une seule instruction fluide, en gérant connexions, fermetures et exceptions.
